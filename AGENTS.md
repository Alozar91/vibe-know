## Cross-document sync (the main way to get this wrong)

A behavioral change is never made in one file. One decision typically requires synchronized edits across the docs:

1. `CONCEPT.md` — the rule itself (§4–13) + «История изменений» row; significant decisions also get a 16.1 entry.
2. `REQUIREMENTS.md` — affected FR/NFR rows + history + traceability §8.
3. `SCENARIOS.md` — affected US scenarios + coverage matrix §5 + history + «Приложение А».
4. `HLD.md` / `LLD.md` — only when the change touches architecture or detailed design; LLD deviates from HLD mechanics via «[уточнение LLD]».

## Decision and versioning conventions

- Significant decisions get a numbered entry in `CONCEPT.md` §16.1, referenced everywhere as «16.1-xx». Small interpretations in REQUIREMENTS are marked «[уточнение]» instead of changing concept decisions.
- Discrepancies found in review are logged as remarks; the concept changes only via §16.1 (REQUIREMENTS §7, SCENARIOS §7). Accepted scenario-review remarks are recorded per round in SCENARIOS «Приложение А».
- Every doc has a top «История изменений» table — append a row for each substantive edit: version, date, summary (which review round, which remarks/decisions). Statuses: «актуальная редакция» vs «черновик для ревью». Version tracks: CONCEPT 2.x, REQUIREMENTS 1.x, SCENARIOS 0.x, HLD 1.x (review rounds), LLD 0.x.
- IDs (FR-xxx, NFR-xxx, US-xxx) are stable: reword in place, never renumber; new items get the next free number. Renumbering breaks the traceability matrix (REQUIREMENTS §8, SCENARIOS §5).
- Cross-reference notation: `(4.1)` = CONCEPT section, `(FR-xxx)`/`(NFR-xxx)` = REQUIREMENTS, `(US-xxx)` = SCENARIOS, `(16.1-xx)` = concept decision.

## Repo quirks

- `.kilo/kilo.jsonc` contains API keys and is intentionally gitignored — never commit it or reproduce its contents.
- Docker Desktop on this machine lives at `C:\Program Files\Docker\Docker\Docker Desktop.exe` (not LOCALAPPDATA); start it manually before compose work — the daemon takes ~1 min to come up. WSL2 distro: Ubuntu, WSL version 2.
- Local toolchain: uv 0.11.x, Node 24 LTS (npm 10.x), Python 3.15 — HLD §4 container versions still govern; local versions only for dev ergonomics.
- Main branch is `master` (no `main`); `docs` branch is a stale copy of the same commit.
- Compose gotchas (discovered stage 1): host port 8000 is occupied by a foreign process → api is mapped to 8001; `minio/mc` is gone from Docker Hub → use `pgsty/mc`; postgres 18 mounts at `/var/lib/postgresql` (not `.../data`); Gotenberg image has no wget/curl (healthcheck = `kill -0 1`); Keycloak has no curl (healthcheck = /dev/tcp probe of mgmt 9000); realm import skips silently if realm already exists in DB (change passwords → `docker compose down -v` or kcadm `set-password`); realm JSON field names are strict (`resetPasswordAllowed`, no `maxTemporaryLockoutMinutes`); realm `passwordPolicy` applies to imported seed users' passwords.
- Cloud deployment (commits 776d7db/ae5e347): `KB_PUBLIC_URL` (http://IP or https://domain) + `KC_HOSTNAME_URL` (issuer; https://domain → `https://domain/auth` with Keycloak behind nginx `/auth/`, port 8080 closed) drive everything — KC_HOSTNAME, issuer, redirectUris realm placeholder `${KB_PUBLIC_URL}`, CORS, VITE_KC_BASE build-arg. Realm import reads them once: set BEFORE first `up` (later change → `down -v` or Keycloak console). nginx gotchas: duplicate `location /` in a server block → container restart-loop (nginx fails `nginx -t`); empty `deploy/nginx/certs/` would also kill the 443 block → `tls-fallback.sh` entrypoint generates a self-signed placeholder (Docker COPY of entrypoint scripts, not a volume mount — mount would shadow nothing on first start but scripts must be in the image).
- Deploy-to-domain gotchas (commits 15a7ed8/83f0023): compose `build.args` reach a Dockerfile RUN stage only after an explicit `ARG NAME` declaration in that Dockerfile — without it the variable is silently empty (SPA bundle built with default `http://localhost:8080/realms/kb`, «Войти» sends users to their own localhost); and `crypto.subtle` exists only in secure contexts (HTTPS or localhost) — on `http://domain` PKCE S256 throws TypeError and the login buttons silently do nothing, so `auth.ts` falls back to PKCE `plain` (S256 returns automatically once TLS is on). But the realm client policy `pkce.code.challenge.method` must match: it is a placeholder `${KB_PKCE_METHOD}` (compose default S256) — on http stands set `KB_PKCE_METHOD=plain` in `.env` and re-import via `down -v`, otherwise Keycloak rejects with «Invalid parameter: code challenge method is not matching the configured one». Uncommitted fixes are lost by `git checkout -- .` — check `git status --porcelain` before reverting.
- Celery child process in kb-worker may hang silently (task logged as "received" but never succeeds; dispatch stalls, events stay `processed=false`) → `docker compose restart worker` fixes it (seen stage 9 twice). Also: worker container command must run beat — it is embedded via `--beat` in `app/worker/main.py` (without it schedules silently never fire).
- Load-testing gotchas (stage 11): a load corpus must be lexically diverse — a ~20-word vocabulary makes every query term match ~90% of documents (GIN useless, p95 10×); keep template «метатермины» (регламент, сводка, мониторинг, термина…) out of the query word list. GIN indexes on search use `fastupdate=off` (migration 0010); compose postgres runs `plan_cache_mode=force_custom_plan` (psycopg3 prepared-statement generic plans killed p95, 698→1612 ms). Re-running acceptance scripts on a live DB accumulates state: old in_review/archived artifacts break "empty list" checks (archive them or clean up), `search_events`/`notification_events` need TRUNCATE/DELETE before analytics assertions. Keycloak introspection requires the introspecting client to be in the token's audience — probe with kb-api credentials (KB_API_CLIENT_SECRET), not kb-cli.
- Test-registration live checks (feature `KB_TEST_REGISTRATION`): `kc_action=register` is silently swallowed when the browser holds a live Keycloak SSO session — it just logs the existing user back in instead of showing the registration form. Do a full Keycloak logout first (`/protocol/openid-connect/logout` + confirm button), then `register()`. SPA logout kills only tokens, not the SSO session. Also: the role-picker dismiss flag is per-user (`kb-rolepick-dismissed:<user_id>` in sessionStorage) — a shared key would suppress the offer for the next user logging in on the same tab.
- RAG/MCP gotchas (branch `rag`, RAG step 5): FastAPI lifespan only runs in `with TestClient(app)` form — a bare `client = TestClient(app)` never enters it, so MCP session manager raises "Task group is not initialized"; Starlette Mount swallows the sub-app's own lifespan, so the host wires `session_manager.run()` via `_wrap_lifespan_with_mcp` in main.py. MCP SDK v2 (2.3.0): `MCPServer` (from `mcp.server`), not FastMCP — `mcp.server.fastmcp` raises ModuleNotFoundError; a tool annotated `-> dict[str, Any]` gets `structuredContent` = the dict itself, bare `dict` annotation → no structuredContent at all; mount with `streamable_http_path="/"` makes POSTs work at `/api/v1/mcp/` (no-slash gets 307) — tests must hit the trailing-slash path. Contextvar set in `verify_token` IS visible in tools (parent task context flows to `tg.start_soon` child), but the reverse isn't — tests set `_principal_var` inside a fake verifier. conftest sets `KB_MCP_ENABLED=0` because `create_app` mounts the real MCP server whose verifier rejects fake tokens; the test fixture unmounts and restores `lifespan_context` after itself (global `app` is shared).
- Stand demo data: `deploy/seed_demo.py` seeds the demo set idempotently (users→KC via kcadm, roles/groups/materials via API), `deploy/cleanup.sql` wipes content tables (one big TRUNCATE — FK cycles materials↔users↔snapshots, attribute_values→attributes/dictionaries, material_tags→tags force a single statement; roles/role_permissions/transition_rules/system_settings/notification_trigger_configs survive). kcadm quirks: comma-joined multi-fields in ONE `-s` (`-s "username=...,email=..."`) fail with error-username-invalid-character / error-invalid-email even for clean ASCII values — pass each field as its own `-s key=value` flag (create with username only, then `update users/{id}` per field); Cyrillic first/last names fail the same way — use ASCII for kcadm-created users. `kcadm.sh config credentials` does not persist across `docker compose exec` invocations reliably (HOME is /opt/keycloak inside container) — the container's `/opt/keycloak/.keycloak/kcadm.config` from an earlier login usually still works, test with a plain `get users` before re-authing. Рецензент without a group review-grant gets 404 (not 403) on in_review materials — predicate §3.2, штатно (FR-067).
- Stand health checks without SSH: Prometheus is published on :9090 — `api/v1/targets` (all 9 jobs up), `api/v1/alerts`, `query?query=kb_backup_freshness_seconds` (fresh < 6 s seen) + nginx `/healthz`, api `/readyz` (postgres+valkey). - Path-MTU black hole (episode 10.11.2026, resolved itself next day): path MTU between operator networks and the server is ~1450 (tunnel 172.28.28.x via msk-ix; `tracepath` from server reports pmtu 1450). ICMP frag-needed reaches the SERVER (its PMTUD adapts; big downloads fine) but not the CLIENT → client-side black hole: big GETs (JWT ≈1560 B) die silently (~19 s → RST, nothing in the nginx log — request headers never arrive), short ones pass. Diagnose from client: `ping -f -l 1416 <server-ip>` (1416 passes, 1424+ dies) plus same-size junk-header curls on every port (80/443/8080/8001 all cut → network, not app; server-pinged-back is inconclusive — Windows firewall blocks inbound echo). Fix client-side: `netsh interface ipv4 set subinterface "<iface>" mtu=1400 store=persistent`. Server side (verified by SSH 11.11): the VPS is an OpenStack VM (MAC fa:16:3e) — ens3 MTU=1450 via DHCP option 26 (provider overlay; explains `tracepath` pmtu 1450 AND why client-side `ping -f -l 1472` fails today: a 1500-B echo REPLY exceeds the VM's 1450 TX cap and is dropped, RX is lenient so big HTTP requests still arrive). The kb_default compose bridge was 1500 ≠ ens3 (created before the provider's MTU change) → containers advertised MSS 1460 over a 1450 link; fixed by pinning `networks.default.driver_opts.com.docker.network.driver.mtu: "1400"` in deploy/docker-compose.yml (needs `docker compose down && up` to recreate bridge+veth; volumes survive). Yesterday's trigger was still operator-side: the death boundary was ~1490–1600 IP bytes (not 1450) — a ~1492-type tunnel on the client's path.
