## 1. Назначение системы

Корпоративная база знаний — централизованная внутренняя система хранения, управления и поиска корпоративных материалов, обеспечивающая единый источник истины для всех подразделений компании.

Система является **универсальной** и работает с любыми типами корпоративных знаний (не только с препаратами или продуктами).

**Главная ценность:** ликвидация разрозненности информации между департаментами и обеспечение полного контроля над жизненным циклом каждого материала с фиксацией ответственных лиц.

## 2. Проблематика

| № | Проблема | Последствия |
|---|---|---|
| 1 | Разрозненность источников | Знания распределены по сетевым папкам, SharePoint, почте, личным файлам |
| 2 | Отсутствие единой точки правды | Информация дублируется и противоречит друг другу в разных отделах |
| 3 | Несогласованность терминологии | Один объект имеет разные названия в разных департаментах (торговое, научное, маркетинговое) |
| 4 | Ручной поиск информации | Сотрудники тратят время на поиск нужного человека или источника |
| 5 | Отсутствие зафиксированного подписанта | Неизвестно, кто утвердил материал и какая версия является финальной |
| 6 | Производные материалы без мастера | Адаптации материала для разных каналов существуют без связи с эталонным источником |

## 3. Цели проекта

### 3.1. Основные цели

1. Создать единое централизованное хранилище всех корпоративных материалов.
2. Внедрить управляемый жизненный цикл с фиксацией ответственных и подписантов.
3. Обеспечить работу с «мастер-материалом» и подчинёнными ему материалами для разных каналов публикации.
4. Предоставить эффективный поиск: по названию, метаданным (включая атрибуты и теги) и тексту (PostgreSQL FTS, частичное совпадение); векторный и гибридный поиск для людей и ИИ-агентов (16.1-120).
5. Обеспечить защиту конфиденциальной информации и полный аудит действий.

### 3.2. Критерии успеха (через 6–12 месяцев после внедрения)

- 100% новых материалов создаются в системе.
- Все публикуемые материалы имеют идентифицированного подписанта.
- Поиск: отклик выдачи (API и интерфейс) — p95 не более 2 секунд; пользовательский сценарий «от открытия системы до нужного материала» — не более 30 секунд.
- Найденность (прокси-метрики вместо неизмеримого «количества обращений "где найти документ Х"»): доля поисковых запросов без результатов снижается; доля поисков, завершившихся открытием материала, растёт.
- ИИ-агенты успешно используют систему как источник данных через API (пост-MVP).
- Критерии измеряются на основе агрегированной аналитики поиска и системных отчётов (см. 9.9, 15.2); целевые НФТ фиксируются на шаге [1] (17).

## 4. Доменная модель

В основе системы лежит **двухуровневая иерархия контейнера и материала**, а внутри материалов — **одноуровневая связь «мастер — подчинённый»**:

```
Группа (контейнер)
└── Материал
    └── (опционально) ссылка на мастер-материал
```

Материал сам является конкретным представлением (файл + опциональный текст); отдельной сущности для представлений нет.

### 4.1. Группа

- Минимальный контейнер с **обязательным названием**.
- Может быть вложенной (вышестоящая группа → подгруппа). Глубина вложенности **намеренно не ограничена**.
- Не содержит специфичных метаданных — только название.
- Название **уникально в рамках вышестоящей группы** (для корневых групп — среди корневых); создание дубликата блокируется. Уникальность проверяется **без учёта регистра** символов и начальных/конечных пробелов; буквы **«е» и «ё» считаются разными** (приведение «ё» к «е» не выполняется).
- Создание, переименование и удаление групп выполняет только **системный администратор**.
- **Пустая группа** (не содержащая ни одной подгруппы и ни одного материала, включая удалённые) удаляется **физически**; перед удалением система предупреждает, если на группу назначены права (снапшоты, 8.1) — записи прав удаляются вместе с группой, операция фиксируется в аудите (12.1).
- **Непустая группа** (есть хотя бы одна подгруппа или материал — в том числе soft-deleted) удаляется только **soft-delete** всей ветки: подгруппы и материалы скрываются, материалы сохраняют свои статусы, но становятся недоступны пользователям, как удалённые (7.9).
- **Ветка не может быть удалена**, если она содержит мастер-материал, у которого есть **неудалённые подчинённые материалы вне этой ветки** (мастер с неудалёнными подчинёнными удалить нельзя — 4.4, 7.9).
- Soft-delete ветки **перекрывает статусное ограничение прямого удаления** (7.9): материалы внутри ветки помечаются удалёнными с сохранением своих статусов; операция фиксируется в аудите (12.1).
- Подчинённые материалы внутри ветки удаляются вместе с ней; их мастер вне ветки не затрагивается и после удаления ветки считается не имеющим неудалённых подчинённых (7.9).
- Удалённые группы **не видны** в дереве и поиске и недоступны по прямой ссылке; просмотр — только системным администратором (служебный раздел); **восстановление запрещено**.
- Удалённые группы **не участвуют в проверке уникальности** названий: название освобождается.
- Перенос подгрупп под другого родителя в первой версии **не предусмотрен**: структура меняется только созданием, переименованием и удалением групп (см. 15.2).

### 4.2. Материал

- Основная сущность системы; находится **ровно в одной группе** и содержит **не более одного файла** (несколько файлов и привязка к нескольким группам не предусмотрены; материал может временно существовать без файла — «пустышка», см. ниже).
- Материал является конкретным представлением: **файл + опциональное текстовое представление** (текст может отсутствовать для видео, презентаций).
- Текстовое представление — **независимое поле**, с файлом жёстко не связано: можно заполнять и файл, и текст одновременно. Для текстовых файлов (Markdown, TXT) при загрузке текстовое представление **заполняется автоматически** содержимым файла; для HTML автозаполнение **не выполняется** — канонический формат представления Markdown, конвертация разметки не предусмотрена (16.1-4); при загрузке или замене **текстового файла (Markdown, TXT)** при непустом текстовом представлении система **предлагает** обновить его — решение принимает пользователь (16.1-112; условия автозаполнения и предложения — 16.1-110; для нетекстовых форматов предложение не выдаётся: содержимое текстового представления не сравнивается с файлом). При отказе в карточке материала отображается признак «текстовое представление не синхронизировано с файлом»; признак снимается при обновлении текстового представления.
- Обязательные поля при создании: **название**, **тип**, **группа**.
- Название материала **уникально в рамках группы** (без учёта регистра символов и начальных/конечных пробелов; «е» и «ё» — разные буквы, как в 4.1); удалённые материалы в проверке уникальности не участвуют (7.9).
- Может быть создан **без файла** (пустышка), файл загружается позже; без файла материал не может покинуть «Черновик» (7.5).
- Метаданные (торговое название, научное название, действующее вещество и т.д.) — это **атрибуты материала**, не группы.
- Типы материалов настраиваются администратором системы через UI.
- Атрибуты — глобальный пул полей, назначаемых на типы материалов.
- Каждый материал имеет собственный статус, жизненный цикл, автора, подписанта и права.
- Поле **«мастер-материал»** (`master_id`) — необязательная ссылка на другой материал.

### 4.3. Связь «мастер — подчинённый»

- **Мастер-материал** — эталонный материал, у которого поле ссылки на мастер **пусто**.
- **Подчинённый материал** — материал, у которого в поле `master_id` указан мастер-материал. Используется для адаптаций мастера под конкретные каналы (сайт, мессенджер, мобильное приложение).
- Подчинённые материалы создаются **позже** мастера, любым пользователем с соответствующими правами. Создание возможно, когда мастер находится в статусе **«Утверждён» или «Публикация»**; группа подчинённого выбирается создателем, проверяется право на целевую группу (8.6). Мастер должен быть **видим создателю** (7.2): для мастера в статусе «Утверждён» это фактически участники процесса.
- При создании подчинённого материала на основе мастера создаётся **физическая копия** файла мастера (не ссылка). Копируется также вся «атрибутика» мастера: текстовое представление, тип, атрибуты, теги. Подчинённый материал создаётся в статусе **«Черновик»** (7.2).
- В диалоге создания выбирается **вид** подчинённого материала: «адаптация» или «перевод». Для перевода в диалоге указывается **язык**: выбранное значение записывается в атрибут «Язык» нового материала (заменяя скопированное от мастера) и подставляется в имя по умолчанию (см. ниже).
- Имя подчинённого материала задаёт создатель; по умолчанию подставляется **«<имя> Адаптация»** (при конфликте уникальности в группе — счётчик к полному имени: «<имя> Адаптация (2)», «<имя> Адаптация (3)», …) — чтобы отличать адаптацию от обычной копии (7.10). Для переводов по умолчанию — **«<имя> (Перевод, <код языка>)»**, код языка берётся из атрибута «Язык» (см. «Переводы» ниже).
- Подчинённый материал можно **отвязать** от мастера (`master_id → NULL`, материал становится самостоятельным) или **сменить мастера**. Новым мастером должен быть материал в статусе **«Утверждён» или «Публикация»**; для подчинённого в статусах «Утверждён»/«Публикация» новым мастером может быть только материал в статусе **«Публикация»** — иначе нарушается правило «подчинённый не публикуется до публикации мастера» (4.4).
- **Перемещать между группами** можно мастеров без неудалённых подчинённых и подчинённые материалы; требуются право «Перемещение» в исходной и целевой группах и право «Редактирование» на материале (8.6); в новой группе название должно быть уникальным; при конфликте операция отклоняется с ошибкой и требованием переименовать материал вручную (автопереименование при переносе не применяется). Мастер, у которого есть неудалённые подчинённые, не перемещается. Явные права материала при перемещении **сохраняются**, наследование пересчитывается по новой цепочке групп; если после перемещения материал станет недоступен работавшим с ним пользователям, интерфейс предупреждает об этом до подтверждения.
- Материал может не иметь подчинённых — тогда он просто самостоятельный материал.
- Подчинённый материал может полностью совпадать с мастером по содержимому.
- **Переводы** документа на другие языки оформляются как подчинённые материалы мастера-оригинала; язык задаётся атрибутом «Язык» из глобального пула (стартовый набор, 6.1). Отдельной языковой сущности («языковых групп») нет (16.1). Значение «Языка» при создании перевода записывается материалу **независимо от назначения атрибута на тип материала** (16.1-115): в поиске участвует всегда (9.7); в карточке отображается/редактируется по правилам 6.1 (если атрибут не назначен типу — в режиме «осиротевшего» значения, только чтение).

### 4.4. Ключевые правила

- Допускается **только один уровень связи**: мастер и подчинённый. Иерархия любой глубины запрещена.
- У мастер-материала ссылки на мастер **нет** (`master_id = NULL`).
- Подчинённый материал ссылается **ровно на один** мастер-материал.
- Мастером может быть только материал, у которого самого нет ссылки на мастер. Подчинённый материал не может быть мастером для другого материала.
- Материал, на который ссылаются подчинённые, не может получить ссылку на мастер (пока у него есть неудалённые подчинённые, 7.9).
- **Циклические ссылки запрещены** (включая ссылку материала на самого себя).
- Подчинённый материал **логически зависит** от мастера.
- Подчинённый материал **не может быть опубликован**, если мастер ещё не опубликован.
- **Смена мастера** запрещена, если подчинённый материал находится в статусах «Утверждён» или «Публикация», а новый мастер не в статусе «Публикация» (иначе нарушается предыдущее правило).
- При изменении мастер-материала подписанты и авторы подчинённых материалов получают **уведомление**. Что считается изменением — определяется настройкой системы: (а) правка файла или текстового представления, либо (б) любое изменение материала.
- При архивации мастер-материала **все неудалённые подчинённые материалы архивируются автоматически независимо от их статуса и группы** — после подтверждения пользователя с предупреждением о количестве (7.8).
- Удаление (soft-delete) мастер-материала, у которого есть неудалённые подчинённые материалы, **запрещено** (7.9).
- **Мастер-материал, у которого есть подчинённые в статусе «Публикация», не может сменить статус** ни на какой другой, кроме «Архива» (каскадная архивация, 7.8). Валидатор проверяет любую смену статуса: и переход по матрице (7.4), и правку контента, которая возвращает материал в «Черновик» (7.7). Тем самым состояние «подчинённый опубликован, а мастер — нет» возникнуть не может; правка метаданных такого мастера (не снимающая публикацию) остаётся доступной.

### 4.5. Следствия модели для проектирования

Проект создаётся с нуля, поэтому ниже перечислены не правки существующего кода, а требования модели к будущим артефактам (требования, HLD, LLD, реализация).

| Область | Требования, вытекающие из модели |
|---|---|
| Модель данных (LLD) | Единая таблица материалов: файл, текстовое представление, статус, автор, подписант, даты публикации/архивации; необязательное поле `master_id` (внешний ключ на эту же таблицу) с индексом |
| Ограничения целостности | `master_id <> id`; мастером может быть только материал без `master_id`; `master_id` нельзя задать материалу, у которого есть неудалённые подчинённые (7.9; триггер или проверка в сервисе); циклы невозможны; уникальность названия материала в группе и названия группы в вышестоящей группе (нормализация: без учёта регистра, обрезка пробелов; «е» и «ё» — разные буквы); смена мастера — только на материал в статусе «Утверждён»/«Публикация», причём для утверждённого/опубликованного подчинённого — только на нового мастера в статусе «Публикация»; перемещение между группами — запрещено только мастеру с неудалёнными подчинёнными; удаление мастера с неудалёнными подчинёнными запрещено; удаление ветки группы запрещено, если она содержит мастера с неудалёнными подчинёнными вне ветки (4.1); мастер с подчинёнными в «Публикации» не меняет статус (кроме «→ Архив», 4.4); удаление материала — только из «Черновик»/«На проверке» (прямое удаление; ветка группы — 4.1) |
| Жизненный цикл | Статусы, матрица переходов, валидаторы и журнал статусов работают на уровне материала; отдельный валидатор «подчинённый не публикуется до публикации мастера»; валидатор «мастер с подчинёнными в «Публикации» не покидает этот статус (кроме «→ Архив»)» (4.4); защищённые системные переходы «Утверждён → Публикация», «* → Архив», запрет исходящих переходов из «Архива»; предустановленные права переходов (7.4) |
| Архивация | Каскад архивации мастер-материала на все подчинённые материалы |
| Права доступа | Иерархия наследования «группа → материал»; связь «мастер — подчинённый» права не наследует; единый каталог прав (8.6) |
| Поиск и индексы | Материал индексируется как единая сущность (название, метаданные, текст); фильтр по признаку «мастер / подчинённый»; права учитываются на уровне материала |
| API | Поле `master_id` в ресурсе материала; операция «создать подчинённый материал» (с копированием файла мастера); в представлении мастера доступен список подчинённых; контракты OpenAPI описываются сразу в этой модели |
| Файловое хранилище | Файл принадлежит материалу; при создании подчинённого материала и при копировании материала создаётся **логически независимый** файл (правки копии не затрагивают оригинал). Физическое хранение — с адресацией по хэшу содержимого (content-addressable): одинаковые копии и версии не дублируются на диске (12.2); выбор технологии — на шаге [3] (17) |
| Уведомления | Триггер «изменён мастер-материал» адресуется подписантам и авторам подчинённых материалов; получатели настраиваются в модели «триггер → типы получателей» (11.2) |
| Аудит и история | События и версии привязываются к материалу; версии хранятся бессрочно, срок аудита настраивается |
| Комментарии | Сущность «комментарий»: материал, автор, дата, текст; комментарий не редактируется и не удаляется, создание фиксируется в аудите (7.6, 12.1) |
| UI | В карточке материала — ссылка на мастер или список подчинённых; действие «создать подчинённый материал»; фильтры в списках и поиске |
| Документация | Функциональные требования, пользовательские сценарии и HLD (раздел 17) пишутся сразу в терминах «материал» и «мастер-материал» |

## 5. Пользователи и роли

### 5.1. Масштаб

- Публикаторов (авторов/редакторов): до 100 человек.
- Читателей: до 500 пользователей.
- Внешних пользователей: **нет**.

### 5.2. Базовые роли (шаблоны)

| Роль | Ключевые возможности |
|---|---|
| Читатель | Просмотр опубликованных материалов согласно правам доступа |
| Автор | Создание материалов (в т.ч. подчинённых), работа с черновиками |
| Рецензент | Проверка материалов, редактирование, одобрение/отклонение |
| Публикатор | Перевод утверждённого материала в статус «Публикация»; архивация материалов (переход «* → Архив», 7.4) |
| Системный администратор | Полный контроль: роли, статусы, настройки, аудит, права |

Состав базовых шаблонов в терминах каталога прав (8.6):

| Шаблон | Права |
|---|---|
| Читатель | Просмотр |
| Автор | Просмотр, Создание, Редактирование, Удаление |
| Рецензент | Просмотр, Ревью (утверждение) |
| Публикатор | Просмотр, Публикация, Архивация |
| Системный администратор | Суперпользователь (8.1) |

Шаблон «Автор» включает «Просмотр»: иначе автор не видел бы собственный материал после публикации (видимость статуса «Публикация» определяется только правом «Просмотр», 7.2). Составы шаблонов редактируются администратором (5.3).

### 5.3. Правила

- Роли являются **шаблонами** с предустановленными правами. Копирование шаблона на объект (группу или материал) — **снапшот**: снапшот действует для всех носителей этой роли; последующее редактирование шаблона на уже скопированные права не влияет (8.1).
- Администратор может редактировать шаблоны ролей через UI.
- Администратор может **копировать права из шаблона** на конкретный объект.
- Помимо базовых ролей существует системная роль **«Все пользователи»**: ей можно выдавать права на объекты (например, чтение корневых групп); она охватывает всех аутентифицированных пользователей. Автоназначения ролей при первом входе нет.
- Управление пользователями и назначением им ролей выполняет **системный администратор**; роли назначаются **в системе** (служебный раздел), Keycloak ведёт только учётные записи и аутентификацию. Сервисные учётные записи создаются в Keycloak, роли-шаблоны им назначаются в системе (10.2). Деактивация пользователя не влияет на его материалы (авторство и фиксация подписанта сохраняются).
- Учётные записи создаёт и деактивирует **системный администратор в Keycloak**: система не хранит пароли и сопоставляет пользователя по идентификатору из токена (13.2). Деактивация в Keycloak запрещает вход; последствия внутри системы описаны выше (материалы, передача права ревью) и ниже (исключение из рассылок). Учётные записи **не удаляются** — только деактивируются; анонимизация при требованиях 152-ФЗ — отдельное решение пост-MVP.
- Обнаружение деактивации системой (16.1-118, механизм — шаг [3], HLD): проверка токенов через introspection Keycloak **на каждом запросе** — немедленный отказ для деактивированных УЗ; периодическая сверка с Keycloak — для служебных последствий: исключение из рассылок, счётчик неархивированных материалов автора, задача «Передать право ревью».
- Если деактивирован единственный носитель права ревью/утверждения в группе, системный администратор **обязан передать это право** другому пользователю (материал не должен «зависнуть» на ревью).
- Ответственность за **актуализацию** материала несёт его автор. При деактивации пользователя система показывает администратору количество его неархивированных материалов, где он указан автором; назначение «преемника» выполняется организационно по регламенту внедрения (17, шаг [6]); поле «владелец материала» и напоминания об устаревании на MVP не предусмотрены (15.3).
- Деактивированные пользователи **исключаются из рассылки уведомлений**.
- Один пользователь может совмещать несколько ролей.
- Нет жёсткого разделения «автор ≠ рецензент». **Подписант — не роль, а фиксируемый факт**: пользователь, утвердивший материал (последний, выполнивший переход в «Утверждён», 7.2).
- Авторство даёт только **видимость** материала (7.2) и **не даёт прав**: «Редактирование» и «Удаление» предоставляются только через роли (8.1, 8.6). Базовый шаблон «Автор» включает права «Просмотр», «Создание», «Редактирование», «Удаление» (5.2) — как следствие, авторы с этой ролью на группе могут редактировать и удалять черновики друг друга (совместное редактирование, 7.11).

## 6. Содержание и структура

### 6.1. Типы материалов

- Примеры типов, атрибутов и значений в документе — из пилотной предметной области (фармацевтика); модель универсальна, пул атрибутов произволен (1).
- Тип = категория (например, «Описание препарата», «Новость», «Регламент»).
- Типы создаются и настраиваются **администратором через UI**.
- Атрибуты (поля) создаются отдельно как **глобальный пул** и назначаются на типы.
- Типы значений атрибута: **строка, число, дата, ссылка, справочник** («ссылка» — гиперссылка URL; ссылки на внутренние объекты системы — пост-MVP).
- Атрибут **«Язык»** входит в **стартовый набор** атрибутов, создаваемый при инициализации системы (заведение — в регламенте внедрения, 17, шаг [6]): от него зависят определение языка материала для поиска (9.7) и имена переводов (4.3).
- **Справочник** — администрируемый список допустимых значений: пользователь выбирает значение из списка (выпадающий список/автодополнение), свободный ввод запрещён. Справочник и его значения ведёт системный администратор; значение нельзя удалить, пока его использует хотя бы один неудалённый материал (7.9).
- Тип значения и признак **многозначности** атрибута **неизменяемы** после создания. Признак **«обязательный»** можно менять: действует для последующих сохранений, существующие материалы не блокируются — проверка выполняется при их следующем редактировании.
- Дополнительные свойства атрибута: признак **«обязательный»** (проверяется при сохранении материала), **многозначность** — список значений для строк, ссылок и справочников (например, несколько действующих веществ или терапевтических областей), **порядок отображения** в карточке материала.
- Смена типа материала требует заполнения обязательных атрибутов нового типа в том же сохранении; если они не заполнены, операция отклоняется с перечнем недостающих полей.
- «Используемый» атрибут/тип: атрибут **нельзя удалить**, пока хотя бы один неудалённый материал имеет его значения; тип материала **нельзя удалить**, пока он назначен хотя бы одному неудалённому материалу (инварианты учитывают только неудалённые материалы, 7.9).
- Исключение атрибута из типа (или смена типа материала) **не удаляет значения**: они сохраняются и отображаются в материалах, но становятся нередактируемыми.
- «Осиротевшие» значения (атрибут исключён из типа материала) показываются в карточке материала в режиме только для чтения, участвуют в поиске и снова становятся редактируемыми, если атрибут вернуть на тип материала.

### 6.2. Поддерживаемые форматы файлов

- Текстовые: Markdown, HTML, TXT
- Офисные: DOCX, XLSX, PPTX
- Графика: PNG, JPG, SVG
- Документы: PDF
- Видео/аудио: форматы, нативно поддерживаемые браузером (MP4/H.264, WebM, MP3 и т.п.); остальные — только скачивание
- **Обязательное требование:** встроенный предпросмотр для всех поддерживаемых форматов; для неподдерживаемых видео/аудио — карточка файла с возможностью скачивания (по праву «Скачивание»).
- Список выше — **базовый набор с гарантированным предпросмотром**. Администратор может расширить список разрешённых к загрузке типов (настройка mime-типов, 16.1-3): файлы типов вне базового набора доступны только для скачивания (право «Скачивание») после антивирусной проверки (13.2), предпросмотр для них не предусмотрен.

### 6.3. Метаданные

**Системные (обязательные):**
- Автор, подписант, последний редактор
- Даты: создания, последнего изменения, публикации, архивации
- Статус материала
- Связанная группа
- Ссылка на мастер-материал (для подчинённых материалов)
- Аудит-лог изменений статусов

**Пользовательские:**
- Произвольные атрибуты (глобальный пул, настраиваются администратором)
- Теги (администрируемый словарь, 6.4)

### 6.4. Теги

- Теги — **глобальный словарь** на уровне системы; словарь ведёт **системный администратор**.
- Пользователь не создаёт теги свободно, а **выбирает из словаря**; при вводе работает **автодополнение** (исключает дубли и опечатки).
- Переименование и слияние тегов выполняет **системный администратор**.
- Тег можно удалить, только если он не используется ни одним неудалённым материалом (7.9).
- Теги участвуют в поиске (9.2) и фильтрах (9.4).

### 6.5. Реализация предпросмотра

- Офисные форматы (DOCX, XLSX, PPTX) конвертируются сервером в PDF (например, LibreOffice headless) и отображаются клиентским PDF-просмотрщиком.
- SVG и HTML **санитизируются** (удаление скриптов); встроенный HTML внутри Markdown вырезается/экранируется при рендере; PDF отображается без выполнения встроенного JavaScript.
- Видео стримится с поддержкой **Range-запросов** (перемотка).
- PNG, JPG, Markdown, TXT отображаются нативно.
- Конвертация офисных форматов выполняется **асинхронно** при загрузке/замене файла — после успешной антивирусной проверки (13.2) — и кэшируется; повторная конвертация только при замене файла. До готовности PDF доступна карточка файла со скачиванием (по праву «Скачивание»); при ошибке конвертации файл остаётся доступным для скачивания, ошибка фиксируется в логах, материал не блокируется.

## 7. Жизненный цикл

### 7.1. Жизненный цикл на уровне материала

**Критически важно:** статус, ревью, утверждение и публикация — это атрибуты **материала**. Каждый материал (в том числе подчинённый) имеет свой независимый жизненный цикл; зависимости подчинённого от мастера описаны в разделе 4.4.

### 7.2. Системные статусы (защищённые)

- **Черновик** — начальное состояние
- **На проверке** — материал отправлен на ревью
- **Утверждён** — признак принятия материала подписантом (подписант и дата фиксируются в момент перехода в этот статус; финальным считается последний подписант)
- **Публикация** — материал опубликован: доступен для просмотра пользователям с правом «Просмотр»; векторная индексация для поиска/RAG выполняется фоновым конвейером (16.1-120, 10.4)
- **Архив** — финальное состояние (без возможности разархивации)

Видимость материалов по статусам:

| Статусы | Кому виден материал |
|---|---|
| Черновик, На проверке, Утверждён | Участникам процесса — автору материала и пользователям с правами «Редактирование», «Удаление», «Ревью (утверждение)», «Публикация», «Архивация» на материал или его группу (право «Просмотр» для них не требуется) — и системному администратору |
| Публикация | Всем пользователям с правом «Просмотр» |
| Архив | Всем пользователям с правом «Просмотр»; в поиске скрыт по умолчанию (фильтр «Включая архив», 7.8), доступен в разделе «Архив» |

Носители прав **«Скачивание»** и **«Копирование»** (8.6) выполняют операции на любом **видимом им** материале (таблица выше) **независимо от его статуса** — включая «Архив»; сами эти права видимость не расширяют: предпросмотр и карточка с содержимым по-прежнему требуют «Просмотр» или участие в процессе. Прямое обращение по ссылке к невидимому пользователю материалу — **ошибка доступа** (8.2, 9.3).

### 7.3. Пользовательские статусы

Пользовательские (кастомные) статусы **не входят в проект**: жизненный цикл состоит только из пяти системных статусов (7.2). Матрица переходов (7.4) и модель статуса закладываются так, чтобы добавить пользовательские статусы пост-MVP без изменения ядра. При добавлении действуют правила: **из финального статуса исходящие переходы запрещены** (7.4); статус с привязанными материалами **нельзя удалить**.

### 7.4. Переходы между статусами

- Настраиваются через **матрицу переходов** (checkbox в UI).
- Для каждого перехода указывается **требуемое право** (можно несколько — достаточно любого из них); право проверяется на самом материале с учётом наследования от групп (8.2, 8.6).
- **Предустановленная матрица при развёртывании** (аналогично уведомлениям, 11.2), далее настраивается администратором: «Черновик → На проверке» — «Редактирование»; «На проверке → Утверждён» — «Ревью (утверждение)» (7.6); «На проверке → Черновик» — «Ревью (утверждение)» (отклонение) или «Редактирование» (отзыв автором, 7.6); «Утверждён → Черновик» (отзыв) — «Ревью (утверждение)» (7.6); «Утверждён → Публикация» — «Публикация»; «* → Архив» — «Архивация» (8.6).
- Переход, у которого право не назначено, **недоступен никому**, кроме системного администратора (default deny, 8.3).
- **Защищённые системные переходы** (нельзя удалить или обойти в матрице): в «Публикация» — только из «Утверждён»; в «Архив» — из любого статуса, кроме «Архива»; из «Архива» исходящих переходов нет (финальный статус, 7.3).
- Достижимость «Архива» из любого статуса гарантирована защищённым переходом «* → Архив».
- Удаление перехода не ломает существующие материалы (они остаются в текущем статусе).
- Система логирует все изменения статусов (кто, когда, из какого статуса в какой).

### 7.5. Валидация переходов

- Файл материала **обязателен** для перевода в статусы «На проверке», «Утверждён» и «Публикация». Текстовое представление **не заменяет файл**: материал без файла не может покинуть «Черновик» при любом заполнении текста, публикация «только текстом» не предусмотрена. Переход в «Архив» разрешён без файла.
- Подчинённый материал нельзя перевести в «Публикация», пока его мастер-материал не опубликован.
- Архитектурно заложена возможность добавления дополнительных валидаторов в будущем.

### 7.6. Процесс ревью

- О материале на ревью уведомляются все рецензенты. **Рецензенты** — пользователи с правом **«Ревью (утверждение)»** на этой группе **или на самом материале**; право публикации само по себе рецензентом не делает (каталог прав — 8.6).
- Рецензент может редактировать материал, находящийся в статусе «На проверке»: право «Ревью (утверждение)» **включает право «Редактирование» только в этом статусе** (8.6); правка материалов в других статусах требует явного права «Редактирование». Правка материала в статусах «Утверждён»/«Публикация» снимает утверждение и публикацию (7.7) независимо от того, кто её выполняет.
- При отклонении материал возвращается в «Черновик», автор получает уведомление. Автор может сам **отозвать материал с ревью** (переход «На проверке → Черновик» с правом «Редактирование», 7.4); инициатор уведомления не получает (11.3).
- Отзыв утверждения: переход «Утверждён → Черновик» с правом «Ревью (утверждение)» — штатная операция для ошибочного утверждения, без правки контента; поле «подписант» очищается (7.7), факт фиксируется в журнале статусов и аудите (7.4, 12.1).
- Количество циклов ревью не ограничено.
- Комментарий при отклонении **не обязателен**; введение обязательности — кандидат пост-MVP.
- Комментарии при ревью — отдельная сущность, привязанная к материалу; видны тем, кому доступен материал, не редактируются и не удаляются, создание фиксируется в аудите (12.1); тред-обсуждения на MVP не предусмотрены. Добавлять комментарии могут **участники процесса** — автор и пользователи с правами «Редактирование», «Ревью (утверждение)» или «Публикация» на материал; отдельное право комментирования на MVP не выделяется.

### 7.7. Публикация, правки и снятие статусов

- Публикуется **конкретный материал** (мастер и подчинённые публикуются независимо, с учётом правила 4.4).
- Перевод из «Утверждён» в «Публикация» — ручной.
- При публикации система фиксирует дату и пользователя, выполнившего публикацию; подписант фиксируется при утверждении.
- При снятии утверждения поле «подписант» **очищается**; история утверждений сохраняется в журнале статусов и аудите (7.4, 12.1).
- **Редактирование** материала в статусе «Публикация» (или «Утверждён») возможно, но **снимает утверждение и публикацию** — материал возвращается в «Черновик». Исключение: правка только метаданных (название, тип, атрибуты, теги) утверждение и публикацию **не снимает никогда**. «Контентные» параметры, снимающие публикацию: файл и текстовое представление — всегда; настройка системы может расширить состав — по аналогии с настройкой «что считается изменением» в 4.4.
- Правка контента в статусе «На проверке» (рецензентом через неявное право, 7.6, или другим участником с правом «Редактирование») **сохраняет статус** — материал остаётся на ревью; автор и рецензенты материала получают уведомление «материал изменён на ревью» (11.1), факт правки фиксируется в аудите (12.1).
- Правка контента мастера, у которого есть подчинённые в статусе «Публикация», **блокируется** валидатором смены статуса (4.4): такая правка вернула бы мастера в «Черновик». Правка метаданных такого мастера разрешена (публикацию не снимает).

### 7.8. Архивация

- Архив = финальный статус, **разархивация невозможна**.
- Архивация мастер-материала → архивация всех **неудалённых** подчинённых материалов (автоматически, независимо от их статуса и группы). Перед выполнением система показывает предупреждение: «Вместе с мастером будет заархивировано ещё N подчинённых материалов» (N — количество неудалённых подчинённых); архивация — только после подтверждения пользователя.
- Архивация подчинённого материала → только этот материал.
- **Обновление эталона с опубликованными адаптациями** — штатная процедура: архивация мастера (каскад с предупреждением) → копия заархивированного мастера становится самостоятельным материалом (7.10) → правка, утверждение, публикация → создание новых подчинённых (4.3). Содержимое заархивированных адаптаций автоматически не переносится; восстановление архивных материалов невозможно.
- Архивные материалы доступны для просмотра (включая предпросмотр), скачивания (право «Скачивание», 8.6) и создания копии (право «Копирование», правила — 7.10); редактирование запрещено.
- В поиске архив скрыт по умолчанию (фильтр «Включая архив»).
- Нужен отдельный раздел «Архив» в интерфейсе.
- Срок актуальности материалов **не предусмотрен** (кураторство и напоминания об устаревании — пост-MVP, 15.3).

### 7.9. Удаление

- Для материалов удаление — только **soft-delete** (физическое удаление не предусмотрено). Правила удаления групп — 4.1 (пустая — физически, непустая — soft-delete ветки).
- Удалить материал можно **только из статусов «Черновик» и «На проверке»** (прямое удаление; удаление ветки группы подчиняется правилам 4.1).
- Мастер-материал, у которого есть неудалённые подчинённые материалы, **удалить нельзя** (см. 4.4).
- **Инварианты «использования»** (у мастера есть подчинённые; атрибут/тип назначен материалу; тег используется) учитывают **только неудалённые** материалы: soft-deleted материалы не блокируют удаление атрибутов, тегов и типов, а также удаление и перемещение мастера и назначение ему `master_id` (4.3, 4.4, 6.1, 6.4).
- **Удалённые материалы не видны в поиске** и **недоступны по прямой ссылке**.
- Удалённые материалы **не участвуют в проверке уникальности** названий (4.2): после удаления название освобождается.
- Просмотр удалённых материалов возможен **только системным администратором** (служебный раздел); **восстановление запрещено**.

### 7.10. Копирование

- Копировать можно материал в **любом статусе**, включая архивный.
- Копирование создаёт новый **черновик**: копируются файл, текстовое представление, тип, атрибуты и теги.
- `master_id` копии сохраняется, если мастер ещё не в архиве; если мастер в архиве — копия становится самостоятельным материалом.
- Подчинённые материалы копируемого мастера **не копируются**: копия — самостоятельный материал (с учётом правила о `master_id` выше).
- Имя копии: «<имя> Копия» (первая копия материала «X» — «X Копия»); при конфликте уникальности в группе добавляется счётчик: «X Копия (2)», «X Копия (3)», …
- Права: право «Копирование» — на исходном материале, право «Создание» — в целевой группе (8.6).

### 7.11. Конкурентное редактирование и смены статусов

- Одновременное редактирование одного материала несколькими пользователями разрешено.
- Коллизии разрешаются **оптимистичной блокировкой**: при сохранении проверяется версия материала; при конфликте пользователь получает ошибку. Merge-интерфейса нет: пользователь открывает актуальную версию и повторно вносит свои правки.
- В API используется версионная проверка (ETag/If-Match).
- Версионная проверка распространяется и на **смену статуса**: переход выполняется только от актуальной версии материала; при конфликте (параллельная правка или другой переход) возвращается ошибка, пользователь повторяет действие.

## 8. Модель прав доступа

### 8.1. Основные принципы

- Права назначаются **на конкретные объекты** (группа, материал).
- У пользователя **нет личных прав** — только через роли.
- Роли являются **шаблонами**, которые копируются на объекты.
- Права **наследуются** от вышестоящего объекта к нижестоящему, если не заданы явно.
- **Нет уровня системы** — права не задаются глобально.
- **Суперпользователь** (системный администратор) видит всё, игнорируя правила.
- **Шаблон роли** — именованный набор прав из каталога (8.6); шаблоны редактирует администратор (5.3).
- **Снапшот** — копия набора прав шаблона роли, назначаемая на конкретную **группу или материал**; снапшот действует для всех пользователей, которым назначена эта роль. Правки шаблона **не влияют** на уже созданные снапшоты (5.3).
- **Эффективное право** пользователя на объект вычисляется по правилам 8.5 из снапшотов всех ролей пользователя, найденных в цепочке «материал → группа → вышестоящие группы».

### 8.2. Иерархия наследования

```
Вышестоящая группа
└── Группа
    └── Материал
```

Права наследуются только по цепочке «группа → материал». Связь «мастер — подчинённый» права **не наследует**: подчинённый материал получает права от своей группы и собственных явных правил.

Группа отображается пользователю **с содержимым**, если право «Просмотр» на неё задано явно или наследуется от вышестоящей группы. Во всех остальных случаях группа отображается **только как путь для навигации** (дерево, хлебные крошки) — без списка содержимого и действий внутри неё. Правило детерминированно разрешает и промежуточные группы, когда права заданы на нескольких уровнях цепочки.

### 8.3. Правила разрешения/запрета

- Для каждого объекта и роли можно задать: **Разрешить** / **Запретить** / **Не задано**.
- **Deny всегда побеждает**, если задан явно на любом уровне иерархии.
- Если права не заданы явно нигде в цепочке — доступ **запрещён** (default deny).

### 8.4. Управление правами

- Только **системный администратор** управляет правами.
- Есть функция **копирования прав** из шаблона роли на объект.
- Есть функция **клонирования роли** (копирование набора прав от одной роли к другой).
- Аудит-лог фиксирует все изменения настроек прав.

### 8.5. Проверка прав при доступе

При проверке права на материал система:
1. Собирает **все** явные правила по всей цепочке: материал → группа → вышестоящие группы.
2. Если найден хотя бы один **Deny** → доступ запрещён (независимо от уровня, на котором задан).
3. Иначе, если найден хотя бы один **Allow** → доступ разрешён.
4. Если правил нет ни на одном уровне → доступ запрещён (default deny).

### 8.6. Каталог прав

Единый перечень прав, назначаемых ролям на объекты. Права, требуемые переходами матрицы (7.4), проверяются **на материале** с учётом наследования от групп (8.2, 8.5):

| Право | Действие | Объект проверки |
|---|---|---|
| Просмотр | Просмотр материала / содержимого группы; включает предпросмотр файла в интерфейсе | Материал, группа |
| Создание | Создание материалов в группе | Группа |
| Редактирование | Изменение материала (файл, текстовое представление, название, тип материала, атрибуты, теги) | Материал |
| Удаление | Soft-delete материала | Материал |
| Ревью (утверждение) | Перевод в «Утверждён», отклонение; определяет рецензентов — на группе или материале (7.6); включает право «Редактирование» только на материалах в статусе «На проверке» (7.6) | Материал (назначение на группе — на все её материалы через наследование) |
| Публикация | Перевод в «Публикация» | Материал |
| Архивация | Перевод в «Архив» (переход «* → Архив», 7.4); входит в шаблон «Публикатор» (5.2) | Материал |
| Копирование | Создание копии материала (7.10) | Материал |
| Перемещение | Перемещение материала между группами (проверяется вместе с правом «Редактирование» на материале) | Исходная и целевая группы |
| Скачивание | Скачивание исходного файла и текстового представления (отдельно, файл .md — 16.1-108); отдельное право, в «Просмотр» не входит | Материал |
| Управление правами | Назначение прав на объект; на MVP право не действует — управляет только системный администратор (8.4), поддержка делегирования — пост-MVP | Объект |

**Кросс-объектные операции** проверяют права на оба объекта:
- создание подчинённого материала — «Создание» в целевой группе; право «Копирование» на мастере при этом **не требуется** (осознанное решение: мастер в статусе «Утверждён»/«Публикация» уже прошёл контроль, адаптация под каналы — штатный сценарий); мастер должен быть видим создателю (7.2);
- перемещение — «Перемещение» в исходной и целевой группах и «Редактирование» на материале;
- копирование — «Копирование» на исходном материале и «Создание» в целевой группе;
- смена мастера и отвязка от мастера — «Редактирование» на подчинённом материале; новый мастер должен быть видим пользователю (7.2).

Целевая группа в кросс-объектных операциях выбирается среди групп, **видимых** пользователю (8.2, право «Просмотр»); назначение «Создание»/«Перемещение» на невидимую группу практического эффекта не имеет.

## 9. Поиск

### 9.1. Типы поиска

| Тип | Назначение | Применение |
|---|---|---|
| Полнотекстовый | Поиск по словам и фразам | Пользователь ищет конкретный документ |
| Векторный (семантический) | Поиск по смыслу через эмбеддинги | ИИ-агенты, аналитика; реализован (16.1-120) |
| Гибридный | Комбинация обоих типов (RRF-слияние) | Универсальный поиск; реализован (16.1-120) |

### 9.2. Что индексируется

- **Название** и **системные метаданные** материала.
- **Названия групп** — глобальный поиск находит группы по имени наряду с материалами (9.4, 9.5).
- **Атрибуты и теги** материала.
- **Текстовое представление** материала (если есть).
- **Содержимое файлов** — НЕ индексируется на старте (возможное расширение в будущем).
- **Комментарии** не индексируются и поиском не охватываются.
- Следствие: материалы без заполненного текстового представления (DOCX, PDF и т.п.) находятся только по названию, атрибутам и тегам. Это **ключевой риск качества поиска** (3.2), поэтому в аналитике (9.9) отслеживается доля материалов с заполненным текстовым представлением; автозаполнение текстового представления при конвертации офисных форматов в PDF (6.5) — **пост-MVP** (15.2, 16.1).

### 9.3. Поиск и права доступа

- Пользователь видит **только доступные ему** материалы.
- В выдачу по умолчанию входят **все статусы, видимые пользователю** (7.2), **кроме «Архива»**: архивный материал попадает в выдачу только при включённом фильтре «Включая архив» (7.8). Участник процесса видит и «Черновик»/«На проверке»/«Утверждён»; фильтр по статусу (9.4) позволяет сузить выдачу, например до «Публикация».
- Если доступен только мастер-материал — подчинённые материалы в выдаче не показываются.
- Поиск и фильтрация учитывают права на уровне материала.

### 9.4. Интерфейс поиска

- Глобальный поиск доступен **на всех страницах** (в шапке).
- Тип поиска выбирается **переключателем** (полнотекстовый / векторный / гибридный; 16.1-120); в векторных режимах сортировка не применяется — порядок задаёт релевантность.
- Сортировка: на MVP — **по релевантности** (ts_rank PostgreSQL FTS для полнотекстовых совпадений, similarity pg_trgm для частичных), а также по названию, дате последнего изменения и дате публикации; в векторном/гибридном режиме порядок задаёт векторная близость / RRF-слияние (16.1-120).
- Фильтры: тип материала, группа (**включает все вложенные подгруппы**), статус, автор (выбор пользователя — в т.ч. для передачи дел при деактивации, 5.3), диапазон дат публикации, атрибуты, теги (несколько выбранных тегов — совпадение любого, ИЛИ — консистентно с any-of многозначных атрибутов, 6.1), архив (скрыт по умолчанию; фильтр «Включая архив»).
- **Операторы фильтров по атрибутам** (по типу значения, 6.1): строка — точное совпадение и подстрока; число и дата — диапазон; ссылка — точное совпадение; справочник — выбор значения; для многозначных атрибутов — совпадение любого из значений.
- **Подсветка совпадений** в результатах.
- **Переключатель** для включения/выключения частичного совпадения.

### 9.5. Логика отображения результатов

- Каждый найденный материал показывается отдельной записью (совпадение в названии, метаданных или текстовом представлении).
- Найденные **группы** (по названию, 9.2) показываются отдельным блоком — только группы, на которые у пользователя есть право «Просмотр» (8.6); выбор открывает группу в дереве.
- Для подчинённого материала отображается ссылка на мастер — **только если мастер доступен пользователю** (иначе ссылка скрывается); для мастера — список доступных подчинённых.
- Фильтр «только мастер-материалы / только подчинённые» возможен.

### 9.6. Частичное совпадение

- Поиск по части названия поддерживается (например, «парацет» находит «Парацетамол»).
- Реализация: триграммы (pg_trgm) в PostgreSQL; ранжирование частичных совпадений — по `similarity` (pg_trgm).
- Включается/выключается переключателем в интерфейсе.

### 9.7. Техническая реализация

- **Полнотекстовый поиск:** PostgreSQL FTS с мультиязычной конфигурацией (русский и английский словари). Состав языковых конфигураций — **настраиваемый параметр системы**; материалы на языках вне конфигурации ищутся без стемминга — их находят частичные совпадения (9.6).
- **Язык материала** определяется атрибутом из глобального пула («Язык», 4.3, 6.1); если атрибут не задан, материал считается **русскоязычным**.
- **Частичное совпадение:** расширение pg_trgm с GIN-индексами.
- **Векторный поиск (16.1-120):** расширение pgvector в том же PostgreSQL; эмбеддинги — по OpenAI-совместимому API; индексация чанков текстового представления — фоновым конвейером (детализация — LLD §7.7).
- **Elasticsearch не используется** (достаточно PostgreSQL для данного масштаба).
- **«е»/«ё» в поиске:** совпадение по «е/ё» определяется правилами FTS-словаря и триграмм и **не гарантируется**; при необходимости вводится нормализация индексируемого текста — отдельным решением, не изменяющим правило уникальности названий (4.1).

### 9.8. API поиска

- **Один эндпоинт** с параметром `search_type` (fulltext / vector / hybrid); реализованы все три типа (16.1-120): fulltext — по FTS-вектору (9.7), vector/hybrid — по чанкам pgvector (детализация — LLD §7.7).
- Результаты учитывают права доступа запросившего пользователя/агента (8.5).
- Дополнительно — `POST /rag/retrieve`: чанки с оценками для RAG-консюмеров (ИИ-агентов) с теми же правами (10.4, 16.1-120).

### 9.9. Аналитика поиска

- Поисковые запросы логируются в **агрегированном виде**: популярные запросы, запросы без результатов, факт открытия материала из результатов поиска (агрегированный CTR — база для критерия «доля поисков, завершившихся открытием материала», 3.2).
- Дополнительно отслеживается **доля материалов с заполненным текстовым представлением** (покрытие поиска текстом, 9.2).
- Назначение: измерение критериев успеха (3.2) и развитие поиска. Персональные данные в отчётах не используются.

## 10. Интеграции и API

### 10.1. Основной принцип

Система работает как **источник данных** (source of truth) с односторонней отдачей информации через API [уточнение, 16.1-114]: система — единый источник истины; API поддерживает интеграционное создание и изменение материалов (включая смену статусов) силами сервисных учётных записей (10.2); **двусторонняя синхронизация** с внешними системами (зеркалирование изменений в обе стороны) не предусмотрена (15.2).

### 10.2. Требования к API

- RESTful API для всех основных операций.
- Аутентификация через **Keycloak** (OAuth2/OIDC): веб-интерфейс и API-клиенты получают и передают токены, выданные Keycloak; API проверяет токены.
- Учёт прав доступа при API-запросах.
- Версионирование API.
- Пагинация, фильтрация, сортировка.
- Интеграции и API-клиенты работают через **сервисные учётные записи** Keycloak: сервисной учётной записи назначаются роли-шаблоны, права проверяются как для обычного пользователя.

### 10.3. Конкретные интеграции

На данном этапе конкретный список систем-потребителей **заранее не определён**: любые внутренние клиенты обращаются к системе по API через сервисные учётные записи (10.2). Архитектура не зависит от состава потребителей и должна допускать подключение любых внутренних систем.

### 10.4. RAG и ИИ-агенты

- Реализовано (пост-MVP шаг [7], 16.1-120): материалы используются как база знаний для LLM через два механизма — REST `POST /rag/retrieve` (чанки с оценками релевантности) и **MCP (Model Context Protocol) сервер** read-only на `/api/v1/mcp` (тулы `kb_search`, `kb_groups`).
- **Права агента = права его учётной записи**: обращение под учётной записью пользователя или сервисной УЗ (10.2); токен Keycloak проверяется introspection (13.2), права применяются тем же предикатом (8.5) — агент видит только то, что видит владелец УЗ.
- Настройка индексации (чанкование по группам, embedding-провайдер) и эксплуатация — контур системного администратора; детализация механики — LLD §7.7.
- REST API остаётся основным каналом интеграций (10.2); MCP — дополнительный, только чтение.

## 11. Уведомления

### 11.1. Триггеры уведомлений

- Материал переведён в статус «На проверке».
- Материал отклонён (возврат в «Черновик» из статуса «На проверке»: отклонение, отзыв с ревью; отзыв утверждения «Утверждён → Черновик» событие не создаёт — 16.1-113).
- Материал заархивирован (одиночная архивация; каскадная архивация подчинённых — отдельный триггер; 16.1-116).
- Событие «материал опубликован» на MVP **не предусмотрено** (16.1-117): публикация — штатный позитивный исход, автор видит статус в «Моих материалах» (15.1) и журнале статусов (7.4); общий триггер «изменение статуса» (выше) может быть включён администратором, если рассылка о публикации нужна; кандидат пост-MVP (15.3).
- Мастер-материал изменён.
- Изменение статуса материала (общий триггер; специализированные триггеры — «на проверке», «отклонён», «каскадная архивация» — имеют приоритет и исключают срабатывание общего для этих переходов, двойных уведомлений нет).
- Подчинённый материал архивирован автоматически (каскадная архивация мастера).
- Правка контента материала в статусе «На проверке» (7.7).

### 11.2. Получатели (настройка)

- Получатели настраиваются администратором в модели **«триггер → типы получателей»**. Типы получателей: **роль-шаблон** (5.2), **документный факт** (автор материала, подписант, последний редактор), **носители права** (например, рецензенты — 7.6).
- Предустановленная конфигурация при развёртывании: «на проверке» → рецензенты материала (право «Ревью (утверждение)» на группе или самом материале, 7.6); «отклонён» → автор; «изменён на ревью» → автор и рецензенты материала (7.7); «мастер изменён» → авторы и подписанты подчинённых материалов; «каскадная архивация» → авторы и подписанты подчинённых материалов; «материал заархивирован» → автор и подписант материала (16.1-116).
- Общий триггер «изменение статуса» по умолчанию **отключён**: включается администратором с выбором типов получателей.
- Деактивированные пользователи исключаются из рассылки (5.3).

### 11.3. Каналы уведомлений

- Каналы: in-app + email. Email активен, если в настройках системы указан почтовый сервер (SMTP); доставка асинхронная, с ретраями и дедупликацией. Настройки уведомлений на уровне пользователя на MVP **не предусмотрены**, но архитектура должна допускать их добавление.
- **In-app:** уведомления отображаются в ленте в интерфейсе со счётчиком непрочитанных; отметка о прочтении — индивидуальная для каждого пользователя. Срок хранения in-app событий — не меньше срока хранения аудита по соответствующим событиям (12.1); дедупликация и дайджест (ниже) применяются согласованно к обоим каналам.
- Анти-шум: события по одному материалу группируются — повторное событие по тому же материалу в окне доставки не создаёт новое уведомление; **уведомление не отправляется инициатору события** (например, автор не получает «отклонён» при собственном отзыве материала с ревью, 7.6); предусмотрен **дайджест** (периодическая сводка, интервал — настройка системы), смягчающий рассылки массовым получателям (например, «все рецензенты группы», 7.6).

## 12. Аудит и история

### 12.1. Аудит-лог

- Фиксирует **все изменения**: создание, редактирование, изменение статусов, изменение прав, архивацию, удаление, скачивание файлов и выгрузку текстового представления (16.1-108); административные операции — создание/переименование/удаление групп, управление типами материалов, атрибутами, справочниками и тегами, изменение матрицы переходов и настроек системы.
- Для каждого события: кто, когда, что сделал, над каким объектом.
- Записи аудита **неизменяемы** (без правки и точечного удаления по запросу); по истечении срока хранения записи удаляются **пакетно по возрасту записи** в соответствии с политикой (13.2).
- Срок хранения аудита — **настраиваемый параметр системы (в днях)**; значение подбирается исходя из требований комплаенса.
- **Просмотры** материалов в аудит не фиксируются (приватность, минимизация ПДн — 13.1); факт открытия материала учитывается только **агрегированно** в аналитике поиска (9.9).
- Системный администратор может **выгрузить журнал аудита в файл JSON** (для проверок и комплаенса); сама выгрузка фиксируется в аудите.

### 12.2. История изменений

- **Версия** создаётся при сохранении с реальным изменением хотя бы одного параметра материала или при загрузке нового файла. В снапшот версии входят: файл (если файл не менялся, версия ссылается на прежний), текстовое представление, название, тип, атрибуты, теги. Изменения статусов, прав и подписанта версией **не являются** — они фиксируются в аудите (12.1) и журнале статусов (7.4).
- В снапшот версии **не входят** `master_id` и права: связи и права не версионируются, их изменения фиксируются аудитом (12.1); восстановление версии не меняет `master_id`.
- Можно посмотреть **старые версии** (включая архивные материалы); версии и журнал статусов (7.4) видны тем, кому виден материал (7.2).
- Просмотр версий включает **сравнение соседних версий**: текстовое представление и метаданные — с подсветкой различий, файл — признак «файл изменён в этой версии» (сценарий ревью после правок, 7.6).
- Версии хранятся **бессрочно**: файл дедуплицируется между версиями (версия без нового файла не дублирует содержимое), поэтому хранение истории дёшево.
- Откат отдельной операцией не предусмотрен; **восстановление старой версии** выполняется как создание новой версии на её основе, при этом применяются правила правки контента (7.7): для материала в «Утверждён»/«Публикация» восстановление снимает утверждение и публикацию (возврат в «Черновик»). Для мастера с подчинёнными в статусе «Публикация» восстановление **блокируется** валидатором смены статуса (4.4).
- Удаление материалов — см. 7.9 (правила удаления приведены там и здесь не дублируются).

## 13. Безопасность и комплаенс

### 13.1. Классификация данных

Система работает со следующими категориями данных:
- Общедоступные (внутри компании) материалы
- Конфиденциальные материалы
- Коммерческая тайна
- Незапатентованные разработки (ноу-хау)
- Персональные данные — присутствуют по построению: учётные записи и имена пользователей (авторы, подписанты, рецензенты), аудит действий, email-рассылки

### 13.2. Ключевые требования

- Аутентификация через **Keycloak** (OIDC). На MVP — вход по логину и паролю; Keycloak позволяет в будущем добавлять другие способы входа (в т.ч. LDAP/Active Directory — пост-MVP, 2FA, SSO) без изменения самой системы.
- Система не хранит пароли: учётными данными управляет Keycloak; система сопоставляет пользователя по идентификатору из токена. Создание и деактивация учётных записей выполняется системным администратором в Keycloak (5.3).
- Гранулярные права доступа на уровнях: группа → материал.
- Полный аудит действий пользователей.
- Шифрование данных при передаче (TLS).
- Шифрование данных при хранении: шифрование дисков/томов сервера (включая БД и файловое хранилище); конкретные механизмы — на шаге [3] (17).
- Защита от утечек конфиденциальной информации: право «Скачивание» и его фиксация в аудите контролируют оригиналы файлов и выгрузку текстового представления (16.1-108) на уровне API. Принятое ограничение: полностью предотвратить сохранение содержимого из предпросмотра (браузерный PDF-просмотрщик) без DRM невозможно; водяные знаки на предпросмотре — кандидат пост-MVP (15.2).
- **Антивирусная проверка загружаемых файлов:** отдельный асинхронный процесс-сканер (очередь проверки файлов); на первом этапе — заглушка с тем же интерфейсом (файлы пропускаются), подключение реального сканера (например, ClamAV) — без изменения архитектуры. Тип файла определяется по содержимому, а не по расширению. Файл недоступен для предпросмотра и скачивания до успешного завершения проверки; при обнаружении вредоносного содержимого файл блокируется, автор и системный администратор получают уведомление.
- Соответствие требованиям к персональным данным (152-ФЗ, внутренние политики): аутентификация и профили — в Keycloak; в системе хранится минимум ПДн (идентификатор, отображаемое имя); email для уведомлений берётся из учётной записи Keycloak (claim токена) и в системе не дублируется (11.3) — за исключением кэша адреса для рассылок, детализация в LLD (шаг [4]); срок хранения аудита (12.1) согласуется с политикой ПДн. Учётные записи не удаляются — только деактивируются (5.3).
- Электронная подпись **не требуется** (достаточно фиксации пользователя и аудита).

## 14. Технические ограничения и требования

### 14.1. Критические ограничения

| Ограничение | Архитектурное следствие |
|---|---|
| Нет бюджета на закупку ПО | Только Open Source компоненты |
| On-premise развёртывание | Полный контроль над инфраструктурой |
| Поддержка силами ИТ компании | Простота эксплуатации, хорошая документация |
| Нет строгого срока | Итеративное развитие, фокус на качестве архитектуры |

### 14.2. Требования к инфраструктуре

- Контейнеризация: развёртывание через **Docker Compose** (single-node); Keycloak разворачивается как отдельный сервис (open source) вместе с системой.
- Резервное копирование и восстановление: снапшоты БД и файлового хранилища согласованы по времени (единая точка восстановления) — иначе восстановление даёт материалы без файлов или осиротевшие файлы.
- Мониторинг и логирование: доступность сервисов (приложение, БД, Keycloak, конвертер офисных форматов, антивирусный сканер, SMTP), глубина и ошибки очередей антивирусной проверки и конвертации (6.5, 13.2), заполненность дисков БД и файлового хранилища, свежесть резервных копий; канал алертинга — email системному администратору (11.3).
- Поддерживаемые браузеры: последние две мажорные версии Chrome, Edge и Firefox (desktop). Базовый набор форматов с гарантированным предпросмотром (6.2) определяется относительно этой матрицы; видео/аудио, не поддерживаемые этими браузерами, — только скачивание (6.2). Мобильные браузеры в матрицу не входят: веб-интерфейс откроется, но корректное отображение не гарантируется (15.2).
- Масштабируемость — **вертикальная** (в рамках single-node): целевая нагрузка (14.3) — до ~10 тысяч документов и до 500 читателей — покрывается ресурсами узла; целевые нефункциональные показатели (время поиска, доступность, RPO/RTO) фиксируются на шаге [1] (раздел 17).

### 14.3. Ожидаемая нагрузка

- Публикаторов: до 100 человек.
- Читателей: до 500 пользователей.
- Объём материалов: до 10 тысяч документов.

## 15. Границы проекта

### 15.1. Входит в проект

- Разработка и внедрение корпоративной базы знаний с нуля.
- Ручная загрузка новых материалов пользователями.
- Полнотекстовый поиск; векторный и гибридный поиск реализованы пост-MVP шагом [7] (16.1-120).
- Гибкая модель прав с наследованием.
- Настраиваемая матрица переходов жизненного цикла (права на переходы, 7.4).
- Аудит и история изменений (включая выгрузку журнала аудита в JSON, 12.1; сравнение версий, 12.2).
- Комментарии (7.6).
- Разделы «Мои материалы» (материалы, где пользователь — автор) и «На проверке» (материалы в статусе «На проверке», где пользователь — носитель права «Ревью (утверждение)», 7.6): быстрая навигация участников процесса, не зависящая от права «Просмотр» на группу (8.2).
- Предпросмотр файлов в веб-интерфейсе.
- Агрегированная аналитика поисковых запросов (9.9).
- Уведомления: in-app + email с настройкой «триггер → типы получателей» (раздел 11).
- Антивирусная проверка загружаемых файлов (13.2; на старте — заглушка).

### 15.2. НЕ входит в проект

- Миграция существующих данных из других систем; существующий контент заносится вручную — решение осознанное, автоматизация загрузки при необходимости оформляется отдельным проектом (16.1).
- Внешние пользователи (партнёры, дистрибьюторы, регуляторы).
- Двусторонняя синхронизация с другими системами.
- Электронная подпись документов.
- Серверный экспорт текстового представления в PDF; печать — средствами браузера из предпросмотра (16.1-109).
- Мобильные приложения (только веб-интерфейс и API).
- Модификация данных через ИИ-агентов: MCP-сервер — только чтение, записи агентами нет (16.1-120).
- Автоматическое извлечение текста из файлов для индексации / автозаполнение текстового представления при конвертации (6.5, 9.2) — приоритетный кандидат пост-MVP.
- Срок актуальности материалов и автоматические напоминания (кураторство — в реестре пост-MVP, 15.3).
- Разархивация материалов.
- Пользовательские статусы жизненного цикла (пост-MVP; см. 7.3).
- Водяные знаки на предпросмотре и DRM-защита (пост-MVP; см. 13.2).
- Интеграция с LDAP/Active Directory (отложено до пост-MVP; подключается через Keycloak).
- Векторный и гибридный поиск, гибридный рейтинг результатов (пост-MVP).
- Отчёты и дашборды (пост-MVP; на MVP аналитика поиска доступна простыми списками в служебном разделе, 9.9).
- Локализация интерфейса: язык интерфейса — только русский.
- Перенос групп между вышестоящими группами (в первой версии; см. 4.1).
- Избранное, подписки на материалы и группы, список «недавних» (кандидаты в пост-MVP).
- Массовые (пакетные) операции над материалами: массовая простановка тегов, перенос, удаление, выдача прав (пост-MVP; операции выполняются поштучно).

Примечание (16.1-120): «Векторный и гибридный поиск» и «RAG и ИИ-агенты» из прежних редакций 15.2 реализованы в пост-MVP шаге [7] (10.4, 9.8); из состава ИИ-возможностей не реализованы: автоматическое извлечение текста из файлов (строка выше) и содержание файлов в индексе.

## 18. Глоссарий

| Термин | Определение |
|---|---|
| Группа | Контейнер, объединяющий материалы и подгруппы по тематике; может быть вложенным, глубина не ограничена |
| Материал | Основная сущность: конкретное представление (файл + опциональный текст; файл может временно отсутствовать — «пустышка», 4.2) с атрибутами, статусом и правами |
| Мастер-материал | Эталонный материал без ссылки на другой материал |
| Подчинённый материал | Материал со ссылкой на мастер-материал (адаптация под канал публикации или перевод, 4.3); создаётся в статусе «Черновик»; допускается только один уровень связи |
| Статус | Текущее состояние материала в жизненном цикле |
| Подписант | Пользователь, утвердивший материал (последний, выполнивший переход в «Утверждён») |
| Рецензент | Пользователь с правом «Ревью (утверждение)» на группе или материале (7.6) |
| Шаблон роли | Предустановленный набор прав, копируемый на объекты |
| Атрибут | Настраиваемое поле метаданных материала |
| Справочник | Тип значения атрибута: администрируемый список допустимых значений; свободный ввод запрещён (6.1) |
| Тип материала | Категория материала (настраивается администратором) |
| Тег | Метка из администрируемого словаря; выбирается с автодополнением, участвует в поиске и фильтрах (6.4) |
| Комментарий | Заметка участника процесса, привязанная к материалу; не редактируется и не удаляется, создание фиксируется в аудите (7.6, 12.1) |
| Матрица переходов | Настройка допустимых переходов между статусами с привязкой к правам (7.4) |
| Снапшот прав | Копия набора прав шаблона роли на конкретный объект (группу или материал); действует для всех носителей роли; последующие правки шаблона снапшот не меняют (5.3, 8.1) |
| Сервисная учётная запись | Учётная запись в Keycloak для API-клиентов и интеграций; права проверяются как для обычного пользователя (10.2) |
| RAG | Retrieval-Augmented Generation: использование материалов системы как базы знаний для LLM (10.4); реализован — REST retrieve + MCP read-only (16.1-120) |
| MCP | Model Context Protocol: открытый протокол подключения ИИ-агентов к данным и инструментам (10.4); в системе — read-only сервер на `/api/v1/mcp` (16.1-120) |
