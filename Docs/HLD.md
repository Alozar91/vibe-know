## 1. Назначение документа и связь с проектом

- Документ выполняет шаг [3] плана (CONCEPT.md, раздел 17): высокоуровневая архитектура — структура системы, технологический стек, модель данных верхнего уровня, общее описание API.
- Входные документы: CONCEPT.md (актуальная редакция), REQUIREMENTS.md (ред. 1.5, FR-001–152, NFR-001–022), SCENARIOS.md (ред. 0.8, US-001–055). Детальное поведение — в этих документах; HLD не переопределяет правила, а фиксирует способ их технической реализации.
- Термины — по глоссарию концепции (CONCEPT.md, раздел 18). Ссылки: (4.1) — разделы концепции; (FR-xxx), (NFR-xxx) — требования (REQUIREMENTS.md); (US-xxx) — сценарии (SCENARIOS.md); (16.1-xx) — решения концепции.
- Охват — **только MVP**; темы пост-MVP затрагиваются только как закладываемые точки расширения (раздел 11; реестр — 15.3 концепции).
- Конкретные контракты API, таблицы, поля, индексы и механизм проверки прав в деталях — шаг [4] (LLD); здесь фиксируются состав сущностей, принципы и выбор технологий. UX/UI — отдельный трек (16.1-33): интерфейсные решения в HLD не принимаются.
- Значимые архитектурные решения, связывающие документы, фиксируются в 16.1 концепции (в настоящей редакции — 16.1-118); внутрисистемные проектные решения фиксируются в этом документе.

## 2. Архитектурные принципы и ограничения

| № | Принцип | Источник |
|---|---|---|
| 1 | Только Open Source компоненты, on-premise развёртывание (проект **экспериментальный** — бюджета на закупку ПО нет; лицензионные ограничения см. примечание после таблицы стека, §4) | 14.1, NFR-015 |
| 2 | Развёртывание Docker Compose, single-node; масштабирование только вертикальное | 14.2, NFR-016 |
| 3 | **Модульный монолит**: один backend-компонент (api) с модулями по подсистемам + отдельный исполнитель фоновых задач (worker); микросервисы не вводятся | 14.1 (простота эксплуатации), 14.2 |
| 4 | Минимум компонентов; PostgreSQL — единое хранилище бизнес-данных **и** поисковых индексов; Elasticsearch не используется | 9.7 |
| 5 | Все длительные операции (антивирус, конвертация, email) — асинхронно через очереди; состояния задач — в БД, отказ вспомогательного компонента не теряет принятые данные | FR-057, FR-059, NFR-005–007, NFR-014 |

| 8 | Аудит неизменяем (append-only), версии бессрочны, файлы — content-addressable хранилище (CAS) без дублирования | 12.1, 12.2, FR-141, FR-147, NFR-010 |
| 9 | Поведение меняется параметрами системы без правки кода (единый реестр настроек) | NFR-020, раздел 5 REQUIREMENTS |
| 10 | Точки расширения без изменения ядра: пользовательские статусы, валидаторы, векторный поиск, настройки уведомлений, MCP | FR-069, FR-077, NFR-022 |

Критические ограничения (14.1) учтены: нет бюджета на закупку ПО (принцип 1), поддержка силами ИТ-компании (принципы 3–4, 9), нет строгого срока — итеративное развитие с фокусом на архитектуре (принцип 10).

### 3.2. Состав компонентов (контейнеры Docker Compose)

| Компонент | Технология | Назначение | Требования |
|---|---|---|---|
| nginx | nginx 1.30 (stable) | TLS-терминация (FR-149), раздача статики веб-клиента, обратный прокси к API и файловым потокам; ограничение размера тела запроса (FR-031) | NFR-016, NFR-017 |
| web-клиент | статика SPA (собирается в образ nginx) | Веб-интерфейс на русском (NFR-018); дерево, карточка, поиск, предпросмотр | 15.1, NFR-017 |
| api | Python / FastAPI (раздел 4) | REST API, бизнес-логика, права, жизненный цикл, поиск, аудит; модули по подсистемам раздела 6 | FR-128–133 |
| worker | Python / Celery | Фоновые задачи: антивирус-заглушка, конвертация, доставка email, обслуживание (очистка аудита и in-app, свёртки аналитики, целостность хранилища silo, сверка с Keycloak) | FR-057, FR-059, FR-136, NFR-005–007, NFR-014 |
| postgres | PostgreSQL 18 | Единая БД: бизнес-данные, версии, аудит, уведомления, права, поисковые индексы (FTS, pg_trgm); отдельная БД внутри экземпляра — для Keycloak | 9.7, NFR-010, NFR-012 |
| keycloak | Keycloak 26.8 | Аутентификация (OIDC), учётные записи, политики паролей, сессии; разворачивается отдельным сервисом | FR-001–006, 13.2, NFR-016 |
| valkey | Valkey 9.1 (BSD-3) | Брокер очередей фоновых задач + кэш; RESP-совместим с Redis (клиенты Celery без изменений); источник истины по задачам — БД (6.4, замечание №4 раунда 1 Приложения А) | NFR-014 |
| silo | Silo (форк MinIO, PGSTY), S3 API | Объектное хранилище — бэкенд CAS: объекты по sha256 (NFR-010), PDF-кэш; S3-совместимый API | FR-147, NFR-010, NFR-012 |
| converter | Gotenberg (LibreOffice headless) | Сервис конвертации офисных форматов в PDF | FR-059, NFR-006 |
| prometheus, alertmanager, node_exporter, postgres_exporter | Prometheus 3-стек | Метрики доступности сервисов, очередей, дисков, свежести бэкапов; алерты — email СА | NFR-019 |
| SMTP | внешний сервер организации | Не разворачивается системой; настраивается параметром при внедрении (раздел 5 REQUIREMENTS) | FR-136, NFR-019 |

Примечания:

- **Антивирус на MVP — заглушка** (16.1-14, замечание №2 раунда 2 ревью заказчика): отдельный контейнер clamav в составе развёртывания **не разворачивается**; проверку имитирует встроенный обработчик worker с тем же контрактом очереди и состояний (6.4) — файл проходит полный конвейер состояний, но всегда завершается «проверено, чисто». Подключение реального сканера (ClamAV 1.5, clamd) в будущем: в worker поставляются обе реализации интерфейса сканера (заглушка и клиент clamd); переключение — параметром конфигурации (+ добавление контейнера сканера в Compose), код api не затрагивается, конвейер 6.4 не меняется (13.2; архитектура закладывается на будущее).
- **Файловое хранилище — silo** (замечание заказчика, ред. 0.8): S3-совместимое объектное хранилище — форк MinIO, сопровождаемый сообществом Pigsty (апстрим MinIO свернул community-редакцию; silo сохраняет S3-совместимость и формат данных). Отдельный контейнер в составе Compose. CAS-принцип сохраняется: система кладёт объекты по ключу sha256 и ведёт FileObject со счётчиком ссылок (6.4) — silo является транспортом/бэкендом, а не источником модели дедупликации. Доступ api/worker — по S3 API c отдельным внутренним сервисным пользователем; браузеру silo напрямую не доступен (файловые потоки — через nginx и api, 6.4). Лицензия AGPL-3.0 — взаимодействие по сети внутри Compose, ограничения не возникают (см. примечание о лицензиях, §4).
- Конвертер — отдельный контейнер, поскольку контроль его доступности и очередей входит в мониторинг (14.2, NFR-019); антивирусный компонент появится в этом контуре при подключении реального сканера.
- Keycloak использует отдельную БД внутри того же экземпляра PostgreSQL — меньше компонентов при сохранении изоляции схемы; перенос в отдельный экземпляр — эксплуатационное решение без изменения архитектуры.
- Все параметры (порты, лимиты, строки подключения, S3-эндпоинт и ключи доступа silo, адрес антивирусного сканера, SMTP) — конфигурация окружения Compose; пароли и секреты — не в репозитории.

## 4. Технологический стек

| Слой | Выбор | Обоснование | Альтернативы (отклонённые) |
|---|---|---|---|
| Backend | Python 3.15, FastAPI, SQLAlchemy 2, Pydantic v2, Alembic | Open Source; быстрая разработка и читаемость; зрелая экосистема (Celery, OIDC-библиотеки); достаточен для нагрузки 100 польз. / 10 000 док. (14.3, NFR-008/009) | Java/Spring Boot (тяжелее в сопровождении малой командой ИТ-компании), Node/NestJS |
| Очереди | Celery 5 + Valkey 9.1 | Стандарт для Python; Valkey — форк Redis под BSD-3 (независимая лицензия, RESP-совместимость); персистентность AOF; состояния задач дублируются в БД (6.4) | RabbitMQ (лишний компонент для single-node) |

### 5.2. Инварианты целостности (проверяются сервисом; часть — на уровне БД, шаг [4])

- `master_id <> id`; мастер — только материал без собственного `master_id`; циклы и ссылка на себя запрещены (FR-032).
- Материал с неудалёнными подчинёнными: не получает `master_id`, не перемещается, не удаляется (FR-032, FR-037, FR-040); удаление ветки группы запрещено при мастере с неудалёнными подчинёнными вне ветки (FR-020).
- Мастер с подчинёнными в «Публикации»: статус не меняется, кроме «→ Архив»; правка контента блокируется (FR-041).
- Подчинённый не публикуется раньше мастера (FR-042); для утверждённого/опубликованного подчинённого смена мастера — только на мастера в «Публикации» (FR-036).
- Уникальность названий: материал — в группе, группа — среди подгрупп родителя; нормализация — lowercase + trim; «е»/«ё» не отождествляются (FR-017, FR-027).
- Инварианты «использования» (подчинённые, значения атрибутов, назначение типа, использование тега) — только по неудалённым материалам (FR-091).
- Оптимистичная блокировка: поле «версия материала» на Material; все изменения контента и смены статусов — через проверку актуальности (FR-093, FR-094); API — ETag/If-Match (FR-095, US-054).
- Файл материала: ссылка на FileObject; отдача и переходы жизненного цикла — только когда FileObject в состоянии «проверен» (сама привязка создаётся при загрузке, до завершения антивирусной проверки); смена контента — через загрузку нового FileObject (безопасность, 13.2).
- Записи аудита неизменяемы (FR-141); комментарии неизменяемы (FR-096).

### 5.3. Что не версионируется и где живёт история

- Не версионируются: `master_id`, права, статус, подписант (FR-144) — их изменения фиксируются в аудите и журнале статусов.
- Восстановление версии — новая версия с применением правил правки контента (FR-148); для мастера с подчинёнными в «Публикации» — блокируется (FR-148, FR-041).
- Сроки: версии — бессрочно (FR-147); аудит — параметр (FR-141); in-app уведомления — не меньше аудита (FR-137).

## 6. Архитектура подсистем

### 6.1. Аутентификация и учётные записи (5.3, 13.2, FR-001–014)

**Потоки OIDC:**
- SPA (браузер): Authorization Code + PKCE; токены — в памяти браузера, refresh-токен; TLS обязательна (FR-149).
- API-клиенты (сервисные УЗ, 10.2): client credentials; роли-шаблоны назначаются в системе (FR-007, FR-013).
- API проверяет токен **introspection** на Keycloak (не локальная проверка подписи JWKS): гарантирует немедленный отказ отозванных/деактивированных УЗ без ожидания истечения токена (FR-011, US-001 A2). Introspection выполняется **на каждый запрос без кэширования** — иначе отзыв допускал бы задержку, недопустимую по FR-011 «немедленно» (см. Приложение А, раунд 1, замечание №12); при нагрузке 100 пользователей стоимость introspection ничтожна; кэширование — возможная оптимизация пост-MVP, только для сервисных УЗ (отзыв которых «немедленность» не требует). Keycloak настраивается на короткое время жизни access-токена (например, 15 минут) — защита в глубину: ограничение окна действия перехваченного токена и страховка на случай будущего включения кэширования (см. Приложение А, раунд 3, №2). При недоступности Keycloak introspection не выполняется — запросы отклоняются (fail-closed); короткая жизнь токена в этой ситуации роли не играет.
- Сессия 8 ч неактивности (FR-005) — временем жизни refresh-токена Keycloak (SSO Session Idle); продолжение работы — повторный вход (FR-005).
- Политики паролей, блокировка перебора, самостоятельный сброс — настройки Keycloak (FR-002–004; параметры — консоль Keycloak, US-048).

**Модель пользователя в системе:** при первом входе с действующим токеном создаётся запись User (по `keycloak_id`, имя — из claim); далее сопоставление по `keycloak_id`; email из claim токена на лету (FR-151, US-040 шаг 1). Пароли системой не хранятся (FR-001).

**Обнаружение деактивации и отзыв сессий (FR-011):** introspection возвращает `active=false` для деактивированной УЗ — все запросы с таким токеном отклоняются немедленно. Дополнительно worker выполняет **периодическую сверку** с Keycloak (Admin API, инкрементально по времени изменения): фиксирует деактивации для исключения из рассылок (FR-139), показывает СА количество неархивированных материалов автора (FR-011) и создаёт задачу «Передать право ревью» при необходимости (FR-012). Зафиксировано решением **16.1-118** (см. Приложение А, раунд 1, замечание №1).

**Подписант и авторство:** фиксируются как документные факты на материале (FR-014, FR-068); для операций сервисной УЗ авторство закрепляется за УЗ (FR-013).

### 6.2. Права доступа (8, FR-099–109)

**Модель:** снапшоты прав (PermissionSnapshot) на группы и материалы, привязанные к ролям (FR-100); наследование по цепочке «материал → группа → … → корневая» (FR-101); Allow/Deny/не задано, Deny побеждает, default deny (FR-102); суперпользователь — в обход (FR-104).

**Единый предикат доступа:** одна функция/модуль вычисляет **эффективные права** пользователя на объект: собирает все снапшоты ролей пользователя по цепочке (8.5), применяет правила Deny/Allow. Этот предикат — единственная точка проверки во всех контурах:

| Контур | Как применяется |
|---|---|
| API/UI операции над материалом | предикат + видимость по статусу (7.2, FR-066) |
| Поиск и фильтрация | предикат на уровне материала; выдача — только видимые материалы (FR-112); группы — только с «Просмотр» (FR-119) |
| Разделы «Мои материалы», «На проверке» | предикат по документному факту/праву ревью, независимо от прав на группы (FR-123, FR-124) |
| Переходы жизненного цикла | предикат + правила матрицы переходов (6.3) |
| Кросс-объектные операции | предикат на оба объекта (FR-108, FR-109) |

**Видимость по статусам** (7.2, FR-066) — ортогональный слой поверх прав: участникам процесса (автор; носители «Редактирование», «Удаление», «Ревью (утверждение)», «Публикация», «Архивация») видны «Черновик»/«На проверке»/«Утверждён»; «Публикация»/«Архив» — носителям «Просмотр». Реализуется в предикате как дополнительный критерий, вычисляемый из тех же снапшотов.

**Производительность:** снапшоты и структура групп кэшируются в памяти процесса api (инвалидация — при изменении прав/структуры групп, события в одном экземпляре); при нагрузке 100 пользователей вычисление предиката по цепочке в БД укладывается в целевые отклики (NFR-001–004). Детали кэширования — шаг [4].

**«Управление правами»:** право в каталоге есть (FR-106), на MVP не действует — правами управляет только СА (FR-105); делегирование — пост-MVP (8.6).

### 6.3. Жизненный цикл (7, FR-065–095)

**Статусная машина** — ядро модуля: статусы 7.2 (FR-065), переходы по матрице (FR-070/071), защищённые переходы (FR-073), переход без права недоступен никому кроме СА (FR-072). Реализация — **цепочка валидаторов** перед фиксацией перехода:

1. **Права перехода** — по матрице через предикат 6.2 (FR-070).
2. **Наличие файла** — для «На проверке»/«Утверждён»/«Публикация» (FR-076, FR-028); «→ Архив» — без файла.
3. **Антивирус** — файл в состоянии «проверен» (FR-058; US-015 A1 — файл отсутствует или не прошёл проверку: переход отклоняется).
4. **Версия** — переход только от актуальной версии (FR-094).
5. **Мастер-зависимости**: подчинённый не публикуется раньше мастера (FR-042); мастер с подчинёнными в «Публикации» не меняет статус кроме «→ Архив» (FR-041); правка контента такого мастера блокируется тем же валидатором.
6. **Каскадная архивация** — при «→ Архив» мастера: предупреждение с числом и подтверждение (FR-039, US-021 шаг 4–5).

Архитектурно: валидаторы — регистрируемый список; добавление новых валидаторов не меняет ядро (FR-077, NFR-022); добавление пользовательских статусов пост-MVP — новые записи матрицы (FR-069).

**Побочные эффекты перехода** (после фиксации статуса, в одной транзакции БД): запись журнала статусов (FR-075), запись аудита (FR-140), генерация событий уведомлений (6.5), фиксация подписанта при утверждении (FR-068), очистка подписанта при снятии (FR-082, FR-084), фиксация даты/пользователя публикации (FR-086), каскадная архивация подчинённых (FR-039).

**Правки по статусам** (FR-084, FR-085, FR-087): правка контента в «Утверждён»/«Публикация» снимает статусы (возврат в «Черновик», подписант очищается); в «На проверке» сохраняет статус и порождает событие «изменён на ревью»; в «Архиве» запрещена; правка только метаданных статусы не снимает никогда (FR-084). Состав «контентных» параметров — настройка (FR-084, раздел 5 REQUIREMENTS).

**Конкурентность:** оптимистичная блокировка полем версии на Material; все мутации, включая смены статусов, — через проверку версии (FR-093, FR-094); API — ETag/If-Match (FR-095); **ETag = версия материала** (см. Приложение А, раунд 1, замечание №7).

### 6.4. Файлы: CAS, антивирус, конвертация, предпросмотр (6.2, 6.5, 13.2, FR-055–064, NFR-010)

**CAS-хранилище:** объекты в silo (S3-совместимое хранилище, 3.2) с ключом по sha256 (`s3://cas/ab/cd/<sha256>`); запись через S3 PUT (атомарность отдельных объектов silo гарантирует); **счётчик ссылок** в FileObject; физическое удаление объекта — только при нулевом счётчике (фоновая задача свёртки; удаление материалов — soft-delete, физическое удаление группы — 4.1). PDF-кэш — в том же хранилище. Модель CAS и механика счётчика — шаг [4]; принцип дедупликации — NFR-010, FR-147.

**Конвейер обработки файла:**

```
загрузка → CAS-запись → очередь антивируса → [проверен]
              │                                │
              │ (блокирован)                   ├─► очередь конвертации (только офисные)
              ▼                                │         │
        файл блокируется,                [PDF готов] ─┤ кэш PDF в CAS
        уведомление автору/СА (FR-058)         │       │ повторная конвертация —
                                               ▼       │ только при замене (FR-059)
                                    предпросмотр/скачивание (FR-060/062/063)
```

- **Загрузка:** тип определяется по содержимому (FR-057); лимит размера — nginx + API (FR-031); материал не блокируется — файл доступен после проверки (FR-058, US-011); объект дедуплицируется по sha256 на уровне silo-ключа и FileObject (см. 7.1).
- **Антивирус:** очередь задач; **на MVP — встроенная заглушка в worker** (16.1-14, замечание №2 раунда 2 ревью заказчика): имитирует проверку с тем же контрактом очереди и состояний (см. Приложение А, раунд 1, замечание №10), отличаясь только ответом «проверено, чисто»; в будущем подключается реальный сканер (ClamAV, clamd) — вызов сканера по сети заменяет вызов заглушки без изменения конвейера; состояния: в очереди → проверяется → проверен / блокирован.
- **Конвертация:** очередь после антивируса; worker вызывает Gotenberg; результат — PDF в CAS; состояния: в очереди → конвертируется → готов / ошибка; при ошибке — скачивание доступно, материал не блокируется (FR-060); повторная конвертация — только при замене файла (FR-059).
- **Отдача клиенту:** файловые потоки через nginx с авторизацией API (X-Accel-Redirect либо подписанный внутренний редирект — шаг [4]); api читает объекты из silo по S3 API и стримит их — браузер к silo напрямую не обращается; видео — Range-запросы (FR-062); отдача — только проверенных файлов (FR-058); права раздельно: предпросмотр — «Просмотр»/участие в процессе (8.6), скачивание — «Скачивание» на видимом материале независимо от статуса (FR-067); скачивание текстового представления отдельным .md (FR-107).
- **Отказ вспомогательных компонентов** (NFR-014): задачи остаются в очереди (состояния в БД) и повторяются с ретраями; потеря данных не происходит; мониторинг наблюдает глубину и ошибки очередей (NFR-019).

**Санитизация на рендере (FR-061):** Markdown — рендер на клиенте с вырезанием/экранированием встроенного HTML (DOMPurify); SVG/HTML — санитизация при отдаче; PDF-просмотрщик без выполнения JS (pdf.js с отключённым JS); видео/аудио — нативно браузером.

### 6.5. Уведомления (11, FR-134–139)

**Генерация:** события жизненного цикла публикуются в транзакции изменения материала в таблицу Notification (получатели вычисляются по TriggerConfig — FR-135; инициатор исключается — FR-138; группировка по материалу в окне доставки — FR-138; сервисные УЗ как автор/подписант — не доставляются, FR-013); отдельный компонент-диспетчер в worker: очередь доставки in-app (≤ 30 с, NFR-007) и email (≤ 5 мин, NFR-007), ретраи, дедупликация (FR-136); при ненастроенном SMTP — in-app работает, email-задачи не создаются (FR-136, US-040 A1); дайджест — периодическая задача worker с настраиваемым интервалом (FR-138).

- **Уведомление о блокировке файла** (FR-058): инициатор события — система (конвейер файлов, 6.4), а не пользователь; правило FR-138 (инициатор не получает) к нему не применяется — получатели фиксированы (автор и СА — US-011 A1). Уведомление направляется напрямую, вне модели триггеров.
- Общий триггер «изменение статуса» по умолчанию отключён; специализированные триггеры имеют приоритет и исключают дубли (FR-134, US-047 шаг 3).

### 6.7. Аудит и версии (12, FR-140–148)

- **Аудит:** append-only таблица; запись — в той же транзакции, что и изменение (FR-140); неизменяемость — отсутствие API правки/точечного удаления (FR-141); пакетная очистка по возрасту — фоновая задача worker (FR-141); выгрузка в JSON — операция СА, сама фиксируется в аудите (FR-143); просмотры не фиксируются (FR-142).

## 7. Общее описание API (10, FR-128–133, NFR-021)

REST API — единственный интерфейс бизнес-логики; веб-клиент работает через тот же API (нет приватных внутренних каналов). Контракты — OpenAPI 3.1, поставляются вместе с системой (NFR-021, US-053 шаг 4); детальные схемы — шаг [4].

### 7.1. Принципы

- **Аутентификация:** Bearer-токен Keycloak; проверка introspection для каждого запроса (6.1, FR-129); сервисные УЗ — client credentials (FR-013).
- **Права:** предикат 6.2 на каждом запросе; ошибки — `401` (нет/невалиден токен), `403` (нет права или объект невидим; прямая ссылка на невидимый материал — 403, FR-067, US-014 A1).
- **Версионирование URL:** `/api/v1/...`; breaking-изменения — новая мажорная версия (FR-130).
- **Пагинация/фильтры/сортировка** — единый стиль списковых операций (FR-131, FR-121): page/per-page (по умолчанию 50), фильтры по 9.4, сортировка по FR-117.
- **Оптимистичная блокировка:** ETag по версии материала; изменение — с `If-Match`; конфликт — `412 Precondition Failed` (FR-095, US-054).
- **Ошибки:** RFC 7807 problem+json, стабильные коды ошибок (шаг [4]).
- **Загрузка файлов:** на уровне материалов/версий операция не идемпотентна — повторная загрузка создаёт новую версию; на уровне CAS контент дедуплицируется: файл с sha256, уже присутствующим в хранилище, привязывается к существующему FileObject (счётчик ссылок +1, повторный антивирус не выполняется — FR-057, NFR-010). Механика — шаг [4].

## 8. Развёртывание, эксплуатация, мониторинг (14.2, NFR-011–019)

### 8.1. Развёртывание

- Docker Compose, single-node (NFR-016); состав — 3.2; масштабирование вертикальное (14.2).
- Ключевые тома: данные PostgreSQL; данные silo (CAS-объекты и PDF-кэш); AOF Valkey; бэкапы.
- Обновление: образы версионных релизов; миграции Alembic применяются при старте api; down-time обновления входит в бюджет доступности 99,5% (NFR-011).

### 8.2. Резервное копирование и восстановление (NFR-012, NFR-013)

- **Единая точка восстановления:** базовая копия PostgreSQL (pgBackRest) + копия данных silo, выполняемые по единому расписанию и согласуемые по времени (14.2); БД Keycloak — в общий контур (учётные записи — 13.2).
- **RPO ≤ 1 ч:** непрерывный WAL-архив PostgreSQL; выгрузка/синхронизация объектов silo с интервалом ≤ 1 ч, согласованные по времени с копией БД (NFR-012); объекты silo неизменяемы (ключ = sha256) — копируются только новые объекты.
- **RTO ≤ 4 ч:** полное восстановление из копии (БД + том + конфигурация Compose); процедура отрабатывается при внедрении (NFR-013, шаг [6]).
- Оценка состава и регламента копирования — вне концепции (16.1-90/91); HLD фиксирует способ достижения RPO/RTO, конкретный регламент — при внедрении.

### 8.3. Мониторинг и алертинг (NFR-019)

| Область | Метрики | Алерт |
|---|---|---|
| Доступность сервисов | api, worker, PostgreSQL, Keycloak, converter, Valkey, silo, nginx (при подключении реального сканера — clamav); SMTP — проверка доступности почтового сервера при настроенном канале (14.2; при ненастроенном — не проверяется) | недоступность > N минут → email СА |
| Очереди | глубина (задач в очереди), возраст старейшей задачи, доля ошибок — антивирус, конвертация, email | рост глубины/возраста/ошибок |
| Диски | заполненность томов БД и хранилища silo | порог % |
| Бэкапы | свежесть последней успешной копии, ошибки pgBackRest/restic | просрочка расписания |
| Приложение | ошибки 5xx, латентность p95 API, длина очереди уведомлений и их доставки, доля ошибок конвертации/сканирования | пороги |

- Канал алертинга — email системному администратору (NFR-019); при ненастроенном SMTP алертинг отключён (US-040 A1) — настройка SMTP при внедрении обязательна, если требуются email-канал или алертинг (раздел 5 REQUIREMENTS).
- **Логи приложений:** api и worker пишут структурированные логи (stdout, собираются Docker); уровень — настраиваемый параметр (реестр 7.2). Содержание: ошибки обработки задач (включая ошибки конвертации — FR-060), отказы интеграций (Keycloak, Gotenberg, SMTP), ошибки 5xx. ПДн и содержимое материалов в логи не попадают; просмотры не логируются (FR-142). Срок хранения и ротация — параметры окружения (NFR-019, 14.2).
- Просмотры материалов мониторингом не фиксируются (приватность, FR-142).
