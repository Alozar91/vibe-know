## 1. Назначение и связь с концепцией

- Документ развивает концепцию (Docs/CONCEPT.md, актуальная редакция) до уровня проверяемых требований — шаг [1] плана (CONCEPT.md, раздел 17).
- Охват — **только MVP**; отложенные темы не детализируются (реестр пост-MVP — CONCEPT.md 15.3), вне проекта — раздел 6 настоящего документа.
- Термины — по глоссарию концепции (CONCEPT.md, раздел 18); ссылки вида (4.1) ведут на разделы концепции; ссылки вида (FR-xxx) — на требования этого документа.
- Каждое требование имеет идентификатор FR-xxx (функциональное) или NFR-xxx (нефункциональное); обратная трассировка — раздел 8.
- Уточнения, принятые сверх концепции при разработке этого документа, отмечены в тексте пометкой «[уточнение]» и фиксируются: значимые решения — в концепции (16.1 №108–110); параметры — в разделе 5; целевые НФТ — разделом 3 (шаг [1] — 14.2 концепции); малые интерпретации, не меняющие решений концепции, — самой пометкой в формулировке требования.
- Формулировка «должен» означает обязательность требования. Целевые НФТ измеримы и проверяются приёмочными испытаниями (раздел 4).

## 2. Функциональные требования

### 2.1. Учётные записи, аутентификация, роли (5.1–5.3, 10.2, 13.2)

| ID | Требование | Концепция |
|---|---|---|
| FR-001 | Система должна выполнять аутентификацию через Keycloak (OIDC); на MVP — вход по логину и паролю. Система не хранит пароли и сопоставляет пользователя по идентификатору из токена. | 13.2 |
| FR-002 | [уточнение] Система (Keycloak) должна обеспечивать самостоятельный сброс забытого пароля: ссылка сброса отправляется на email учётной записи; требуется настроенный SMTP. При ненастроенном SMTP сброс пароля выполняет системный администратор средствами Keycloak. | 13.2, 11.3 |
| FR-003 | [уточнение] Политика паролей: минимум 8 символов и символы не менее трёх категорий (строчные, прописные, цифры, спецсимволы). | 13.2 |
| FR-004 | [уточнение] Защита от перебора пароля: после 5 неудачных попыток входа подряд учётная запись временно блокируется на 15 минут. | 13.2 |
| FR-005 | [уточнение] Сессия пользователя завершается после 8 часов неактивности; для продолжения работы требуется повторный вход. | 13.2 |
| FR-006 | Учётные записи создаёт и деактивирует только системный администратор в Keycloak; удаление учётных записей не предусмотрено. | 5.3, 13.2 |
| FR-007 | Роли назначаются пользователям в системе (служебный раздел); Keycloak ведёт только учётные записи и аутентификацию. | 5.3, 16.1-101 |
| FR-008 | Система должна содержать пять базовых шаблонов ролей (Читатель, Автор, Рецензент, Публикатор, Системный администратор) с составами прав по 5.2; шаблоны и их составы редактирует системный администратор через UI. | 5.2, 5.3 |
| FR-009 | Системная роль «Все пользователи» охватывает всех аутентифицированных пользователей; автоназначение ролей при первом входе отсутствует. | 5.3 |
| FR-010 | Один пользователь может совмещать несколько ролей. | 5.3 |

| FR-012 | Если деактивирован единственный носитель права ревью/утверждения в группе, система должна требовать от администратора передать это право другому пользователю [уточнение]: при деактивации в служебном разделе появляется задача «Передать право ревью»; её нельзя закрыть, пока право не назначено другому пользователю (US-044); работа остального СА не блокируется. | 5.3 |
| FR-013 | API-клиенты работают через сервисные учётные записи Keycloak; роли-шаблоны назначаются им в системе; права проверяются как для обычного пользователя. [уточнение] Авторство и фиксация подписанта операций, выполненных сервисной УЗ, закрепляются за ней; уведомления, адресованные автору/подписанту — сервисной УЗ, не доставляются (по аналогии с FR-139). | 10.2, 11.2 |
| FR-014 | Подписант — фиксируемый факт (последний, утвердивший материал), а не роль; авторство даёт только видимость материала, без прав. | 5.3, 7.2 |

## 6. Вне MVP (осознанные исключения)

Полные перечни — CONCEPT.md 15.2 (вне проекта) и 15.3 (реестр пост-MVP). Ключевое и добавленное настоящим документом:

- Миграция существующих данных; массовый импорт (отдельный проект при необходимости).
- Внешние пользователи; двусторонняя синхронизация; электронная подпись; мобильные приложения.
- Пользовательские статусы. Векторный/гибридный поиск и RAG/ИИ-агенты реализованы пост-MVP шагом [7] (16.1-120; FR-133, FR-153) — исключены из перечня; модификация данных агентами остаётся вне проекта (MCP — только чтение, 10.4).
- Автоматическое извлечение текста из файлов (автозаполнение текстового представления при конвертации офисных форматов) — приоритетный кандидат пост-MVP; от покрытия текстом зависит качество поиска (9.2, 15.2).
- Отчёты и дашборды; массовые операции; избранное/подписки/«недавние».
- Кураторство (владелец, срок актуальности, напоминания); водяные знаки и DRM; LDAP/AD, 2FA, SSO.
- Перенос групп между вышестоящими группами; делегирование управления правами.
- [уточнение, 16.1-109] Серверный экспорт текстового представления в PDF; печать — средствами браузера из предпросмотра.
- Принятые ограничения: содержимое предпросмотра не защищено от сохранения без DRM (13.2); совпадение по «е/ё» в поиске не гарантируется (9.7); содержимое файлов не индексируется (9.2).

## 7. Критерии приёмки требований

- Требование считается выполненным, если поведение системы соответствует формулировке при проверке способами из раздела 4 (для НФТ) и по сценариям шага [2] (для FR).
- Каждый FR проверяется на соответствие концепции: расхождение концепции и требований недопустимо без внесения решения в 16.1 концепции.
- НФТ проверяются приёмочными испытаниями на окружении, эквивалентном целевому (single-node, NFR-016), при пиковой нагрузке (NFR-008).
